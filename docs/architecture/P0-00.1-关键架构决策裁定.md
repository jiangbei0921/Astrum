## 2. 第二部分：8 项设计缺口裁定（G1–G8）

> 每项给出：已有设计 / 未解决 / 实际影响 / 建议方向 / 是否必须在 P0 确定 / 对契约的影响。

### G1 · 事件模型

- **已有设计**：`05` §7 有 phase 状态图（INIT→UNDERSTAND→…→DONE，约 150 行 `switch`）；`15` §1.1 有 `trace[]`、§4.2 有 `checkpoints[]`。没有 `Event` 实体、没有事件类型、没有事件顺序或持久化约定。
- **未解决**：什么算一个事件、事件与 trace/checkpoint 的关系、是否持久化、是否允许监听。
- **实际影响**：不定义也能跑（状态机靠 phase），但「事件驱动状态图」只剩 phase 枚举；调试与恢复只能靠 `trace` 文本，无法机器校验。
- **建议方向（轻量，明确不要事件总线）**：
  - 采用**事件记录（event log），不是事件总线**：`TaskState.events: Event[]`，只追加、不订阅、不派发。
  - `Event{seq, at, taskId, type, stepId|null, payload}`；`type` 限定 8 类：`phase.changed / step.started / step.ok / step.failed / step.skipped / progress.decided / verdict.issued / task.aborted`。
  - 生命周期：P0 仅定义结构与 `append()` 语义（不写盘）；P2 内存态；P4 与 checkpoint 一起落盘（可只存关键事件）。

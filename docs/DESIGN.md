# ASTRUM 设计文档

版本 1.8 · 天文多智能体工作台
本文件说明产品定义、多来源体系、智能体分工、执行流程、知识分级、界面方向与数据治理。全文不含代码，也不作为运行说明。

---

## 一、产品定位

### 1.1 一句话

说一个时间、一个地点、一个名字，回答「现在能看到什么、在哪里、怎么找、凭什么」。

### 1.2 三条设计原则

1. **事实与表述分离。** 星历与文献构成事实层，永远由本地计算与核验，不经过网络；来源只决定这份事实被如何讲述。
2. **结论必须有出处。** 观测数字标注「实时计算」，知识结论标注来源、核验日期与共识等级。
3. **不确定时必须说不知道。** 宁可给出「无法确证」，也不生成看似合理的内容；前沿与推测性内容单独标注。

### 1.3 与通用助手的差异

| 维度 | 通用对话助手 | ASTRUM |
| --- | --- | --- |
| 事实来源 | 模型参数记忆 | 本地星历计算 + 带来源的知识条目 |
| 时间敏感 | 常给过期天象 | 按当前上下文实时解算 |
| 可执行性 | 停在结论 | 方位、高度、窗口、器材、月光干扰 |
| 不确定性 | 倾向补全 | 显式降级并声明边界 |
| 表达来源 | 单一模型 | 可切换本地策略或云端模型，事实不变 |
| 学术严谨性 | 单一语体 | 专业/科普双表述 + 共识等级 |
| 多轮一致性 | 常丢失上下文 | 记忆主体并做指代消解，数值不漂移 |
| 交付前自检 | 无 | Critic 逐项检查证据并给出门槛结论 |

## 二、多来源体系

### 2.1 为什么要拆成两层

天文问答里，**数字错了比讲得不好严重得多**。因此把回答拆成两层：

- **事实层**：天体坐标、升落时刻、可见窗口、月相、知识条目、来源与共识等级。始终由本地星历与知识库产出，任何来源都无法改写。
- **表述层**：把事实组织成一段人话。可以由不同来源承担——本地策略，或云端大模型。

这样切换来源时，界面上的数字一个都不会变，变化的只是语气、详略与叙事方式。答案顶部固定显示「事实」与「表述」两个标签，切换后下一轮回答立即反映。

### 2.2 可用来源

**本地策略（免配置、离线可用）**

| 来源 | 定位 | 差异 |
| --- | --- | --- |
| ASTRUM 内核 | 默认 | 按问句特征自动选择语体与深度 |
| 内核 · 研究视角 | 专业语体 | 事实链更长，专业表述优先，适合核对参数 |
| 内核 · 科普叙事 | 科普语体 | 短句与类比优先，事实条数收敛 |

三者共用同一套事实，差异来自语体、深度与语气，因此可以随时对照而不会产生数值分歧。

**联网检索（需网络、可引用原文）**

新增一路「检索」来源。它并行向多个**支持跨域**的公开端点发请求，谁先返回可用结果就用谁：

| 端点 | 内容 | 跨域 |
| --- | --- | --- |
| NASA 图库 | 天文影像与任务说明 | 允许 |
| OpenAlex | 学术文献与摘要 | 允许 |
| Semantic Scholar | 学术文献检索（标题/摘要/年份/DOI） | 允许 |
| 维基百科 Core REST | 条目摘要 | 回显来源 |
| 维基百科 Action API | 条目摘要（备用） | 允许 |

检索优先使用解析出的实体名（例如「猎户座大星云」）而不是整句提问；返回结果做一次二元组重合过滤，剔除明显跑题的条目。答案中会标注本次由哪个端点提供、耗时多少。若全部失败，自动回退本地索引并标注「本地索引」，同时给出各端点的失败原因与「检测连通」入口，不伪装成联网结果。

说明：部分网络环境下维基与 DuckDuckGo 不可达，因此不把它们作为唯一来源；百度百科接口虽可达，但不返回跨域头，浏览器内无法直接调用，故未采用。Semantic Scholar 匿名调用共享限流配额，出现 HTTP 429 属常态，此时该端点退出竞速并如实说明原因，其余端点继续。

**云端模型（需密钥、仅负责表述）**

采用**统一配置入口**：先选供应商，再按所选模型动态展开所需参数，取代「每家一张卡片、各填各的输入框」的做法。

| 供应商 | 默认模型 | 接口形态 | 备注 |
| --- | --- | --- | --- |
| OpenAI | gpt-4o-mini | OpenAI 兼容 | 通用表达与追问强 |
| Anthropic | claude-3-5-sonnet-latest | Anthropic Messages | 长文组织、表述谨慎 |
| Google | gemini-1.5-flash | Gemini 原生 | 多模态、长上下文 |
| DeepSeek | deepseek-chat | OpenAI 兼容 | 中文表达自然 |
| Moonshot | moonshot-v1-8k | OpenAI 兼容 | Kimi 系列，中文长文本 |
| 智谱 | glm-4-flash | OpenAI 兼容 | GLM 系列，语义与工具调用 |
| 通义千问 | qwen-plus | OpenAI 兼容 | 百炼平台 |
| Mistral | mistral-small-latest | OpenAI 兼容 | 欧系开源模型，推理快 |
| Groq | llama-3.3-70b-versatile | OpenAI 兼容 | LPU 低延迟推理 |
| xAI | grok-2-latest | OpenAI 兼容 | 长上下文 |
| 自定义 | — | OpenAI 兼容 | 任意自建代理 / 本地推理网关 |

动态参数面板按供应商能力显示：**模型版本**（预设下拉 + 自定义模型 ID）、**API Key**、**Base URL**、**温度**、**最大输出 tokens**。每家供应商附独立的「配置步骤」折叠区与密钥创建入口。

配置项按供应商分别保存，切换供应商不会丢失已填内容；面板提供「测试连接」（最小请求往返 + 状态落库）与「设为默认」两个动作。任何一次保存都会立即刷新侧栏与顶栏的可用状态。云端只收到整理好的事实清单、参考表述与最近三轮对话记忆，系统提示明确要求「不得引入新的数字、名称或年代」「记忆中出现的数值必须保持一致」「事实不足时只解释已有事实」。模型返回后还会做一次**数值一致性核验**：输出中出现在事实层之外的数字会被点名提示，并要求以「依据」章节为准。

### 2.3 能力差异如何呈现

不编造跑分，只呈现**功能维度**与**运行状态**：

- 功能维度：能否复算星历、有无引用来源、能否离线、是否需要联网、是否依赖密钥。
- 运行状态：离线可用 / 未配置密钥 / 待测试 / 已连通 / 连接失败（附原因）/ 已停用。
- 实测指标：每次调用后记录延迟与字符数，显示在表述卡右上角。

来源浮层按「本地策略」「云端模型」两组排列，每项显示状态、供应商、模型名、能力标签与一句定位描述。侧栏保留精简列表与「查看全部」入口。

### 2.4 密钥与网络

- 密钥只保存在本机浏览器，不上传，界面明示。
- 浏览器直连云端普遍会被 CORS 拦截，失败时如实报告原因，并提示填写自建代理地址。
- 未配置密钥时选择云端来源，不会伪造回答：答案中插入一张虚线「回退说明卡」，说明本次表述仍由本地内核生成。

### 2.5 三种工作模式

1. **单一来源**：按当前选中的来源回答。
2. **并行对比**：始终可用。固定展示「本地内核」一列，再加「联网检索」一列（失败时给出本地索引或失败原因），若已连接云端模型再加一列。事实层仍只有一份，对比的是叙事与补充信息。
3. **回退**：云端调用失败时自动回退本地，答案中保留失败原因与「数值未受影响」的说明。

## 三、智能体体系

### 3.1 十一个内置智能体

| 名称 | 中文 | 职责 | 可调参数 |
| --- | --- | --- | --- |
| Muse | 缪斯 | 意图解析、任务分派、汇总裁剪、边界核验 | 语气、深度、知识范围、推断尺度 |
| Vega | 织女 | 知识检索与事实供给，缺失时降级并标注 | 知识范围、专业侧重、深度 |
| Cosmos | 宇宙 | 黑洞、大爆炸、暗物质、暗能量、引力波 | 知识范围、专业侧重、深度、推断尺度 |
| Nova | 新星 | 爆发天体：超新星、变星、脉冲星、磁星、伽马暴 | 专业领域、知识范围、深度 |
| Helios | 赫利俄斯 | 太阳活动与空间天气：日面活动、太阳风、极光判据 | 专业领域、器材倾向、深度 |
| Kepler | 开普勒 | 星历计算：坐标、升落、中天、窗口、月相 | 数值精度、深度 |
| Horizon | 地平 | 观测条件：暗夜窗口、月光、光害、器材 | 器材倾向、深度、知识范围 |
| Orion | 猎户 | 空间可视化：星盘投影、连星、定位路径 | 星图风格、深度 |
| Lyra | 天琴 | 语体切换与叙事组织，不改写数字 | 语气、知识范围、深度 |
| Curator | 编目 | 并行对比时合并多来源的重复事实点，保留差异与冲突 | 证据门槛、深度 |
| Critic | 评议 | 交付前逐项复核证据条数、数值来源、共识标注、边界声明与置信度 | 证据门槛、知识范围、深度 |

协作链路按真实工作流固定排序：解析（Muse）→ 事实与领域判断（Vega / Cosmos / Nova / Helios）→ 计算（Kepler）→ 观测条件（Horizon）→ 可视化（Orion）→ 表述（Lyra）→ 合并（Curator）→ 复核（Critic）。

### 3.2 十个行为参数

语气风格、回答深度、知识范围、专业侧重、推断尺度、数值精度、器材倾向、星图风格、**专业领域**、**证据门槛**。参数只影响表达方式与侧重，不改变任何数值——这一点在编辑器与设置中都写明。

- **专业领域**：通用 / 太阳系 / 致密天体 / 恒星与星系 / 深空观测。决定 Vega 与 Nova、Helios 的取材偏向。
- **证据门槛**：严格 / 均衡 / 开放。Critic 据此决定是否强制插入「本次结论仅为线索」的边界声明。

### 3.3 自定义智能体

可新建任意数量，与内置并列。可定义身份（名称、中文名、标识字符、主题色、一行职责）、参与范围（哪类问题唤起它）、十个行为参数、回答章节开关、专家注记（不超过两百字）、优先级与启用状态。

行为参数在提问处理前生效，因此会改变整份回答的语气与结构；章节开关会移除对应部分，协作链路同步裁剪，不会出现「声称画了星图却没有图」；注记以该角色名义插在追问建议之前。自定义智能体同样不能改变事实层。

提供儿童科普、严谨研究、天文摄影三套快速模板。

### 3.4 历史记忆机制

会话内保留最近八轮「问题 / 结论要点 / 主体」三元组，用于三件事：

1. **指代消解**：当问句只有「它 / 那个 / 这颗」而没有实体时，回溯最近一轮的主体并还原（答案顶部标注「承接上文：××」）。还原后仍走同一套星历与知识库，数值不因记忆而改变。
2. **数值一致性**：还原出的主体与最近三轮摘要一并作为「对话记忆」发给云端模型，要求其沿用同一主题与同一数值。
3. **一致性复核**：Critic 检查答案中是否给出共识等级、核验日期与边界声明。

「新对话」会同时清空界面与记忆，避免跨主题串味。记忆只存在于当前会话内存，不写入本地存储。

### 3.5 Critic 评审闭环

每个答案在交付前都会经过一次固定检查，结果以「评审结论」章节呈现：

| 检查项 | 判定标准 |
| --- | --- |
| 证据条数 | 依据章节是否有结构化事实 |
| 数值可复算 | 是否由本地星历计算得到，或明确标注为引用型结论 |
| 共识等级 | 是否标注 established / emerging / speculative 与核验日期 |
| 边界声明 | 是否存在未知/时效/安全提示 |
| 置信度 | 是否达到该问题类型的最低可信度 |

门槛设为「严格」时，任一未达标项都会触发额外的边界声明，强制把结论降级为线索；「开放」允许在证据不足时给出方向，但同样标注缺口。这一机制借鉴了 AstroAgents 的 Critic 角色，但检查维度按天文学的事实层/表述层分离重新定义，不直接照搬其新颖性评分。

### 3.6 Curator 合并去重

并行对比模式下，多个来源的表述常有大量重复。Curator 以标题归一化后的前缀为键做合并：重复项折叠为一条并注明「与某某表述一致，已合并去重」，不同项原样保留，不做静默取舍，也不隐藏来源分歧。

## 四、执行流程

1. **解析**：识别意图、抽取天体与别名、解析日期与城市；缺省项取观测台上下文。
2. **消解**：问句只有代词时，从会话记忆还原主体，并在协作链路中标明还原结果。
3. **分派**：按意图选择智能体组合（新增 nova 爆发天体、helios 太阳与空间天气两条专用路径）。
4. **计算**：星历采样当日高度角，求升落与中天；观测侧求暗夜窗口并按高度、亮度、月光加权评分。
5. **组装**：按语体生成段落，生成可视化，附加来源与共识等级；太阳系天体额外补入「实测面貌」清单。
6. **表述**：若选择了云端来源，把事实清单、参考表述与最近三轮记忆交给该模型，只取回一段叙事文本；失败则回退，返回后做数值一致性核验。
7. **合并**：并行对比时由 Curator 折叠重复表述，保留差异。
8. **接管**：命中的自定义智能体覆盖参数、裁剪章节、附加注记。
9. **核验**：Critic 逐项检查证据、数值来源、共识标注、边界声明与置信度，必要时插入边界声明并给出「评审结论」。

## 五、输出结构

答案自上而下固定七段，并在最上方加一条来源说明。

1. **来源条**：事实层（本地星历 + 知识库）与表述层（当前来源），云端调用时附延迟；承接上文时额外显示「承接上文：××」。
2. **协作链路**：参与的智能体与各自动作摘要。
3. **结论**：一句可执行判断，配一行上下文。
4. **表述卡**：由当前来源提供的叙事；云端失败时为虚线回退说明；数值越界时附核验提示。
5. **依据**：结构化事实表、语体段落、来源清单；若答案涉及具体天体，会出现「在实时星图中查看」按钮，点开即以该目标的方位为中心的全屏星图。
6. **观测建议 / 共识等级 / 可视化 / 实测面貌 / 边界声明 / 评审结论**：按问题类型出现。
7. **追问建议**：三个可点击的下一问。

页脚显示置信度、共识等级、时效、核验日期、参与智能体数与计算时刻。

## 六、知识共识分级

| 等级 | 含义 | 例子 | 界面 |
| --- | --- | --- | --- |
| 已成共识 | 多手段独立验证，无实质分歧 | 大爆炸宇宙学、微波背景、恒星演化、引力波 | 青色徽标 |
| 前沿研究 | 有观测迹象但未定，或方法间存在张力 | 暗能量演化、哈勃张力、暴胀、JWST 早期星系 | 金色徽标 + 复核提示 |
| 未定论 | 缺乏可检验预言，属推测 | 多重宇宙 | 红色徽标 + 不可引用提示 |

同一等级配一段「仍需回答的问题」，说明争议具体在哪，而不是笼统标注「不确定」。

知识条目同时维护专业表述与科普表述，切换只改措辞，不改事实。

## 七、不确定性与边界

**三级响应**：可计算 → 标实时复算；可引用 → 给条目、来源、置信度、共识等级；不确证 → 明确声明并列出可回答方向。

具体机制：显式日期与事件表不符时直说无记录；目标恒在地平线下时改为「全年不可见」并说明纬度原因；未指定城市时按默认城市计算并注明经纬度；计算异常降级为边界卡；太阳观测强制滤光提示，月食则明确肉眼安全。

明确不做：天气预报与云量、实时极光、精密定轨与掩星时刻、器材品牌推荐、占星运势、生成天体图片冒充实拍、超出年度表的日月食路径承诺。

| 太阳系天体 | 直径、距离、周期、卫星数、温度 | NASA Planetary Fact Sheet（2023 版） |
| 星球实测面貌 | 大红斑收缩、北极六边形、卡西尼缝、奥林帕斯山高度、水手谷长度等 | NASA / ESA / JPL 任务发布（2025-06 核验） |

时效分四级：长期稳定、年度表、实时计算、需在线更新；界面各有对应芯片。数值若来自模型拟合，标明前提（如「在标准宇宙学模型下」）；同一事实存在多个测量时给出区间或分歧，不取单一数字冒充共识。

### 8.1 NADC（国家天文科学数据中心）数据治理

中国科学院国家天文科学数据中心（NADC / China-VO）作为国家科技基础条件平台，统一为 LAMOST、FAST、Gaia、银河画卷、天文底片等大科学装置提供「原始数据传输—归档—备份—产品归档—发布—共享—在线分析—数据融合」的全生命周期服务。其发布数据集均带 **DOI + CSTR 双标识**。

本产品据此建立两条引用纪律：

1. **只引用已公开发布的版本。** 每条条目写明数据版本（如 DR14 v0、DR21、CSC v2.0、MWISP DR1）与核验时间，不引用未发布或申请中的数据。
2. **获取方式必须标注。** 公开下载、需邮件申请（如 FAST 科学数据需联系 FAST 数据中心）、许可限制（如 Gaia-ESO 需 CC BY 4.0 并致谢 ESO）三者分开写明，避免用户误以为可直接下载。

已纳入的 25 条 NADC 相关知识条目覆盖四类：巡天与星表（LAMOST、FAST、Gaia DR3、银河画卷、LHAASO、Chandra、eROSITA、Euclid）、时域与变星（AST3-2、ZTF、公众科学超新星、天文底片数字化）、太阳物理与地基观测（太阳物理历史数据、国内核心地基望远镜、卫星激光测距）、中国设施与前沿发现（天关/SVOM/慧眼联合观测、LAMOST+Gaia 长周期变星、太阳鱼骨状结构）。前沿成果一律标为「前沿研究」并附「仍需回答的问题」。

### 8.2 星球实测数据的更新纪律

太阳系天体的「实测面貌」只收录任务已公开发布的观测结论，并逐条标注来源任务与年份，例如：

| 天体 | 实测内容 | 来源任务 |
| --- | --- | --- |
| 木星 | 大红斑直径由约 40,000 km 缩至约 16,000 km；极区 8 个多边形气旋 | 哈勃、朱诺号（2016–） |
| 土星 | 北极六边形急流（直径约 30,000 km）；卡西尼缝宽约 4,800 km | 卡西尼-惠更斯（2004–2017） |
| 火星 | 奥林帕斯山高约 22 km；水手谷长约 4,000 km、深约 7 km | MRO、好奇号、毅力号 |
| 金星 | 云顶风速约 100 m/s，4 天绕行一周；南北极各一对稳定气旋 | 金星快车、Akatsuki |
| 水星 | 卡洛里盆地直径约 1,550 km；全球半径收缩约 7 km | MESSENGER（2011–2015） |
| 月球 | 艾特肯盆地直径约 2,500 km、深约 13 km；极区水冰 | LRO、嫦娥四号、嫦娥六号 |
| 海王星 | 大暗斑（1989 年）在 1994 年哈勃观测中已消失 | 旅行者 2 号、哈勃 |

更新方式：任务发布新结果时更新对应条目的 `updated` 字段与正文，并在数据来源处注明任务与年份。**未由任务直接成像或确认的内容一律不写**；存在争议的结论（如金星磷化氢）在条目中显式标注为未定论。

### 8.3 借鉴与致谢

本产品的多智能体编排在「评审—回流」闭环、多来源去重合并、严格 JSON 输出约束与提示词透明化四点上有意借鉴了开源项目 **AstroAgents**（Saeedi 等，arXiv:2503.23170，ICLR 2025 Workshop，MIT License，https://github.com/amirgroup-codes/AstroAgents ）。AstroAgents 面向质谱数据与天体生物学假设生成，其业务域与本产品不同，因此**只借鉴工程与流程范式，不引入其 Python 依赖（langchain / pymupdf4llm），也不迁移其领域提示词**；其 Critic 的评分维度按天文学的事实层/表述层分离重新定义。致谢声明在设置页「帮助 → 数据与边界」中同步展示。

## 八·五、太阳系观测视图

### 8·5.1 定位

一个**居中的、可交互的 3D 太阳系观测场景**，与既有 2D 星空视图并列：2D 视图回答「此刻天空中什么在什么方位」，3D 视图回答「太阳系整体是什么结构、这颗天体长什么样、有多大、有多重、绕着什么转」。

### 8·5.2 数据与渲染

- **位置**：直接复用 `Astro.helio()`（JPL 近似根数），与 2D 星图同源同刻；月球按各卫星真实轨道半径与周期做圆轨道近似。
- **贴图**：不加载外部位图（破坏离线承诺），改为按 NASA/JPL 已公开的实测特征参数程序化烘焙等距圆柱投影图（木星纬向带纹与南纬 22° 大红斑、火星水手谷与奥林帕斯山与极冠、金星超旋转云顶、月球月海、太阳米粒组织与临边昏暗等），再按法线做逐像素 Lambert 合成。
- **光照**：太阳方向为唯一光源，晨昏线软化；恒星自发光不做外部光照；地球/金星/泰坦有大气辉光；土星环按真实内外径与卡西尼缝分带绘制，近侧半环压在行星之上。
- **尺寸**：八大行星与 21 颗卫星的直径比例严格等于真实比例，只用一个全局统一放大系数 `boost` 整体缩放；太阳按固定屏幕尺寸绘制（否则会覆盖整个内行星区），其真实半径在信息面板中给出。
- **距离布局**：默认压缩 `r ∝ a^0.5`，可一键切换为严格等比 `r ∝ a`；页脚实时标注当前公式与放大系数。

### 8·5.3 交互与编排

三档层级（全系 / 近景 / 特写）、拖动旋转、滚轮推拉、双击聚焦、悬停提示、点击选中高亮、标签与轨道显隐、放大滑杆、时间档位与暂停，全部键盘可达（1/2/3 切层、Tab 循环天体、L 标签、R 重置、Esc 关闭）。

问答侧新增 **Navigator（领航）** 智能体与 `system-view` 意图：把「打开太阳系」「聚焦土星」「隐藏轨道标签」「放大天体」解析成固定结构的动作（`action / target / fields / state / next`），由界面层执行并回填执行结果；目标不存在时给出最近候选而不做猜测。

## 九、界面与交互

### 9.1 视觉方向：日光纸感

上一版是「深夜天文台」——全暗背景、金色点缀、正文衬线。本版整体转向**日光纸感**：暖白纸底、墨色正文、电光靛蓝作为唯一强调色、白色浮起卡片配细边框与极浅投影。

星图与月相不再跟随页面配色，而是收进**深色观测窗**：浅色界面里嵌一块近黑的圆角视口。这样既保留了天文观测的现场感，也让数据区域与文字区域有明确的视觉分工。

排版上仍保留衬线字体，但只用于两处：首屏标题与答案结论句。其余全部使用无衬线，形成「编辑感标题 + 清晰正文」的对照。

### 9.2 布局结构

- **顶栏**：品牌、当前来源胶囊（点击切换）、观测台开关、设置、新对话。
- **左侧栏**：回答来源（精简列表 + 查看全部）、智能体（点击配置）、试试这样问。移动端收为抽屉。
- **主区**：首屏是英雄区——标题、说明、居中的输入框、四张能力卡；发出第一条消息后，输入框下沉为底部对话栏，英雄区收起，对话流占据主位。
- **右侧观测台**：观测上下文、实时星图、今晚优先、月相与暗夜。宽屏常驻并可一键折叠，中屏与窄屏改为浮层。

### 9.3 交互要点

- 来源切换有三个入口：顶栏胶囊、输入框内的来源按钮、左侧来源列表；三者同源同步，切换后立即反映在胶囊状态与下一条答案的来源条上。
- 未配置密钥的云端来源可被选中，但会即时提示「本次仍由本地内核生成」，不做静默失败。
- 星图视角：**天球（球体）视图**。以观测者所在位置建立地平坐标系，把一个完整球面正交投影出来，相机可绕球旋转；球面上叠赤经赤纬网格、天赤道（青色）、地平圈（金色）、天极与天顶标记、银道带；地平线以下的星点压暗但保留，构成一颗可翻转的透明天球。
- 星图交互：拖动水平旋转天球、垂直改变俯仰，滚轮缩放（70%–220%），双击复位；点击任意恒星、深空天体或行星弹出资料卡（类型、星等、坐标、此刻高度方位、所属星座、共识等级与摘要），可直接追问。
- 全部标注：恒星中西名与拜耳编号（到 3.8 等）、深空天体编号、行星高度与星等、月球实时相位、星座名与缩写、参考圈名称。右下角另嵌一颗以观测者为中心的小地球，画出昼夜线与「你在这里」。
- 地点：支持三种方式——按 IP 自动定位、检索全球 779 个城市与首都、直接输入经纬度（如 39.9,116.4）。跨时区地区按 IANA 时区换算，含夏令时。
- 键盘：回车发送、Shift+回车换行、`/` 聚焦输入、Esc 关闭所有浮层。
- 链接直达：问题、来源、设置、智能体、观测台均可通过地址参数直接打开，便于分享与演示。
- 首屏与对话态共用同一个输入框组件，避免两套交互逻辑。

## 十、质量保障

1. 数值交叉验证：目标中天高度应等于 90° 减纬度与赤纬之差；北极星高度随纬度浮动；南半球应判定恒在地平线下。
2. 回归测试：对意图路由、实体解析、日期解析、边界分支逐条构造问句。
3. 链路一致性：章节被裁剪时同步裁剪协作链路。
4. 状态隔离：回答生成过程深拷贝配置，一次提问不污染后续行为。
5. 布局校验：以整页宽度与滚动宽度比对确认无横向溢出，再逐断点截图核对。
6. 持久化容错：本机存储不可用时降级为内存态。

## 十一、已知局限

- 云端接入受浏览器跨域限制，未配置代理时通常无法直连；这是产品当前最主要的落地障碍。
- 密钥以明文存于本机浏览器存储，不适合共享设备。
- 无在线数据：云量、空间天气、彗星、新发现只能声明不可用。
- 升落时刻未计入地形遮挡与异常折射，山区与高纬偏差可达数分钟。
- 星座连线为示意骨架，非国际天文联合会官方边界。
- 联网检索依赖外部接口，可能因网络或跨域策略失败；此时只展示本地索引，并在标题上标注，不冒充联网结果。
- 维基百科返回的语言变体由接口决定，个别条目可能仍是繁体。
- 星图为正交投影的天球示意，不做真实地形遮挡与大气折射修正；地平线以下的天体仍以暗色显示，便于理解天球结构。
- IP 定位依赖第三方服务（ipapi.co），离线或被拦截时只能手动选择；定位精度到城市级，不适用于精确到街区的需求。
- 城市数据集覆盖首都与人口较大的城市，小城镇需用坐标方式输入。
- 会话记忆只保留最近八轮且不落盘；跨会话不继承主体、也不继承地点。
- 自定义智能体的注记按原文呈现，不做语义解析。
- 星球实测面貌随任务发布更新，当前快照核验于 2025-06，最新任务结果需以机构原始发布为准。
- Semantic Scholar 匿名调用共享限流配额，高频使用会频繁触发 429。
- NADC 相关条目只覆盖可公开获取的数据集；FAST 内部数据、申请中数据与受限数据不在收录范围。

## 十三、交付形态与构建约定（v1.5）

### 13.1 双形态交付

| 形态 | 文件 | 适用场景 | 约束 |
| --- | --- | --- | --- |
| 单文件自包含 | `astrum-standalone.html` | 发送给他人、任意路径打开、在线预览 | 752 KB，不可再手工编辑 |
| 多文件 | `index.html` + `assets/` + `core/` + `data/` | 本地开发、二次修改 | 目录不可拆散 |

**为什么需要单文件形态**：多文件架构的固有脆弱点是 `index.html` 与 `assets/ core/ data/` 必须同目录。一旦分离（单独拷贝文件、单文件预览沙箱、目录拆散），全部外部子资源 404，页面会退化成**无样式裸 HTML**且 JS 静默不执行 —— 用户看到的只是一堆无法使用的文字。单文件形态把 CSS 与全部 JS 内联，从交付层面消除这一类故障。

### 13.2 启动守卫

多文件版在 `</body>` 前注入自诊断脚本：检测 8 个核心模块（`Astro` / `CATALOG` / `KNOWLEDGE` / `AgentCore` / `Sources` / `SolarView` / `OBSPLAN` / `SOLAR`）是否就位，缺失时显示全屏提示页，说明缺失模块、原因与两套修复方案。同类故障因此能自我诊断，而非静默降级。

### 13.3 CSP 与内联脚本

- CSP 保持严格模式，**不放开** `'unsafe-inline'`；内联脚本一律用 `sha256` hash 精确授权。
- **关键陷阱**：HTML 解析器会把脚本内容的 CRLF / CR 归一化为 LF，CSP hash 必须按归一化后的字节计算。失配时浏览器**静默拦截**（控制台有 CSP 违规日志，页面无任何报错，功能全失），排查成本高。
- `tools/sync-csp-hash.js` 同步 `index.html` 的内联脚本 hash（支持 `--check` 只校验）。
- `tools/build-standalone.js` 生成单文件版并重算全部脚本 hash。

### 13.4 构建与回归流程

```bash
node tools/sync-csp-hash.js      # 改过 index.html 内联脚本后同步 hash
node tools/build-standalone.js   # 重新生成单文件版
node tools/selftest.js           # 20 项功能回归（零依赖）
```

`tools/selftest.js` 采用「注入断言脚本 → `chrome --dump-dom` 读回」实现，不引入 puppeteer / ws，保持项目零依赖定位。**多文件版必须原地测试**（复制到临时目录会使相对路径失效）。

### 13.5 已知边界

- 单文件版体积 752 KB，不适合作为网页在线发布的首选（多文件版更轻）。
- 构建产物与源码分离，任何脚本改动后必须重新构建，否则单文件版 hash 失配会被 CSP 拦截。
- 服务端代理、请求签名、鉴权仍需后端工程，纯静态架构无法承载；明确不做 CDN 引入，以免破坏「零依赖、可离线、可双击」的定位。

## 十四、IP 定位降级链（v1.6）

### 14.1 问题

「按 IP 定位」按钮弹出「IP 定位不可用（网络或跨域限制），请手动选择地点」。实测根因：

```bash
curl -s "https://ipapi.co/json/"    # → HTTP 403，Cloudflare "Just a moment..." 人机校验页
```

原实现只依赖 `ipapi.co` **单一端点**，且 `r.json()` 直接解析 —— 遇到 403 的 HTML 挑战页时抛 `SyntaxError`，被 `.catch` 兜底成一句笼统的"网络或跨域限制"，**误导用户以为是本地网络问题**。

### 14.2 方案：四端点顺序降级 + 失败原因归类

| 顺序 | 端点 | 字段 | 实测状态 |
| --- | --- | --- | --- |
| 1 | `ipwho.is` | `latitude` / `longitude` / `timezone.id` | 200，可用，无 key 需求 |
| 2 | `ipinfo.io` | `loc`（`"lat,lon"`）/ `timezone` | 200，可用 |
| 3 | `ipapi.co` | `latitude` / `longitude` / `timezone` | **403**（Cloudflare 拦截） |
| 4 | `api.ipapi.is` | `lat` / `lon` / `timezone` | 200，可用 |

每个端点配一个 `parse` 适配器把异构字段归一化为 `{lat, lon, city, region, cc, tzid}`，上层只认统一结构。

**失败原因分类**（区别于笼统报错）：

| 原因 | 判定 | 提示 |
| --- | --- | --- |
| `blocked` | HTTP 403/429，或响应含 `just a moment` / `challenge` / `captcha` / `<html` | 定位服务被网络策略拦截，请手动选择地点 |
| `timeout` | `AbortController` 超时（6s/端点） | 定位服务超时，请手动选择地点 |
| `server` | HTTP ≥ 500 | — |
| `network` | `Failed to fetch` / `NetworkError` | — |
| `parse` | JSON 解析失败或坐标缺失 | — |

失败后**自动聚焦地点输入框**（支持直接输入 `39.9,116.4` 坐标），并按原因给出差异化提示。

### 14.3 设计要点

- 整体超时 20s，单端点 6s —— 4 个端点串联也不会让用户干等。
- CSP `connect-src` 放行 `ipwho.is` / `ipinfo.io` / `api.ipapi.is`（不放行 `*`）。
- 归一化时区字段：`ipwho.is` 的 `timezone.id`（IANA 名）与其余端点的 `timezone`（字符串）形态不同，解析时分别处理。

### 14.4 验证

| 项 | 结果 |
| --- | --- |
| 降级链真实联网 | ✅ `lat=35.690 lon=139.692 city=Tokyo` |
| UI 端到端（点击按钮） | ✅ 200ms 内 toast「已按 IP 定位：东京」，地点框同步更新 |
| 故障注入（ipwho.is 强制失败） | ✅ 自动降级到 ipinfo.io 成功取数 |
| CSP 违规 | 0 |

## 十五、全球地点检索（v1.7）

### 15.1 问题

1. **输入的地址不全** —— 地点输入框只匹配内置的 809 座城市（GeoNames cities15000 子集），
   输入「黄山风景区」「Mauna Kea」「Eiffel Tower」「Lofoten」等一律无结果。
2. **IP 定位不精确** —— 定位到「济南」但坐标是**城市中心点**（36.67, 117.00），
   旧逻辑一律吸附到 40 km 内的城市，丢弃了 IP 接口返回的真实经纬度。

### 15.2 方案：三路互补的在线检索

把 GeoNames 全量（300 万+）打进包里不现实，改为在线检索为主、本地库兜底：

| 端点 | 数据源 | 特点 |
| --- | --- | --- |
| **Open-Meteo Geocoding** | GeoNames 全量人口地名 | 自带中文名 + IANA 时区 + 人口 + 行政层级；覆盖乡镇（PPL）/县区（PPLA）/山峰（MT）/机场（AIRP） |
| **Photon (Komoot)** | OpenStreetMap | 覆盖自然地标与地标性建筑；无时区字段，需按坐标反查 |
| **timeapi.io** | IANA 时区库 | 按坐标返回 IANA 时区名，补齐 Photon 结果的时区 |
| 本地 809 城市 | GeoNames 子集 | 离线兜底，断网时仍可检索 |

三者均无需 API key，CSP 逐域名放行（不放行 `*`）。

### 15.3 关键实现细节（都是实测踩出来的）

| 问题 | 现象 | 解法 |
| --- | --- | --- |
| 本地化名导致英文搜不到 | 搜 `Reykjavik` 返回「雷克亞維克」，匹配不上 | Open-Meteo 同时请求 `language=zh` 与 `language=en`，用 `id` 关联合并，中文名显示、英文名参与匹配 |
| `mergeEn` 取错字段 | 英文名始终没生效 | `enList` 元素是 `parse()` 产物，名称字段是 `n` 不是 `name` |
| 同名结果排序错乱 | 搜 `Reykjavik` 排出加拿大地名；搜 `Interlaken` 排出美国小镇 | 引入 `popRank` 档位：按 GeoNames `feature_code` 编码「作为该名字正主的可信度」（首都 6 / 一级行政区 6 / 二级 5 / 三级 4 / 一般聚居地 2），与 OSM 的 `place` 类型对齐 |
| 跨源同点判定失败 | 瑞士因特拉肯（46.6839, 7.8664）与 Photon 同地（46.6855, 7.8585）相差 0.63 km 却未合并 | 不用 `toFixed` 字符串键（在四舍五入边界会不一致），改用**球面距离阈值 1.5 km** |
| 地标召回不足 | 搜 `Eiffel Tower` 前几名是加拿大山峰 | Photon 对多词查询追加**词序反转**与**去末词**两个变体 |
| Photon 并发被拒 | 同时发 3 个变体请求 → 全部 `Failed to fetch` | 变体请求**串行**执行，并给 `fetchJSONRetry` 加一次退避重试 |

### 15.4 交互改造

原生 `<datalist>` 换为自建检索面板：

- 输入即搜（本地匹配 0 延迟先出，在线结果异步补入），防抖 220 ms
- 面板显示：名称 · 行政层级 · 国家 · 类型标签 · 精确坐标
- 键盘：↑↓ 移动、Enter 选中、Esc 关闭；点击外部关闭
- 请求序号丢弃过期响应，避免快速输入时结果错乱
- 保留坐标直输（`39.9,116.4`）与「坐标」按钮

### 15.5 IP 定位精度修正

- 旧：`nearestPlace(lat, lon, 50000)` → 一律吸附到 40 km 内城市中心
- 新：**优先采用 IP 接口返回的真实经纬度**；仅当本地城市库在 3 km 内命中才吸附（可带波特尔等级等本地属性）
- 叠加 Photon 反查（`/reverse`）补充区域名，失败不影响主流程

### 15.6 测试工具

| 工具 | 作用 | 用法 |
| --- | --- | --- |
| `tools/geotest.js` | 全球地名检索回归（16 个用例，校验国家码 + IANA 时区） | `node tools/geotest.js` |
| `tools/selftest.js` | 全功能回归（27 项断言，含 GeoSearch 与地点检索） | `node tools/selftest.js [file-url]` |

`geotest.js` 单独存在的理由：headless Chrome 跑多请求联网测试时，容易因
`--virtual-time-budget` 耗尽而挂起（多个 5s 超时的 fetch 串联时尤其明显）。
Node 22 自带 `fetch` / `AbortController`，可以直接 `require` 模块跑真实请求，
结果稳定可复现，不依赖浏览器。

### 15.7 IP 定位的时间预算

降级链是**串行**的（并发会被 IP 服务限流），所以总耗时 = 各端点耗时之和。
初版设的是「单端点 6s × 4 端点 = 24s」，但 `locateByIP` 的整体超时只有 20s，
两者打架，且 20 多秒的等待对用户不可接受。

最终取值：

| 参数 | 值 | 说明 |
| --- | --- | --- |
| 单端点超时 | 4s | 实际按「剩余预算」动态裁剪，不超过 4s |
| 整体预算 | 12s | `fetchIPChain(4000, 12000)` |
| 兜底提示超时 | 15s | 超过即提示「定位超时，请手动选择地点」 |
| 预算耗尽 | 剩余 < 1.5s 时不再尝试下一个端点 | 直接收敛失败并给出分类提示 |

这样即使全部端点都不可达，用户也只需等 12~15 秒，且提示会说明原因
（被拦截 / 超时 / 不可用），而不是笼统报错。

## 十六、检索、证据与答案合成（v1.8）

本节记录对「联网检索 → 证据 → 答案」链路的系统性重建。
审计过程与问题清单见 `docs/AUDIT-search-evidence.md`，实施方案见 `docs/PLAN-search-evidence.md`。

### 16.1 修复的核心缺陷

| # | 缺陷 | 根因 | 修复 |
| --- | --- | --- | --- |
| 1 | 所有检索实际都在搜同一个词 `Naos` | `sources.js` 的 `withRetry(ep.fn, 2)` 未把 query 传给端点函数，`fn()` 以 `undefined` 执行；`enQueryFor('')` 又命中了星表中 `cn` 为空的恒星 | `withRetry(fn, tries, args)` 透传参数；`enQueryFor` 对空查询直接返回空串；`search()` 入口拒绝空查询 |
| 2 | 检索结果从不进入答案 | web 分支先用本地知识库生成完整答案，检索结果只 `splice` 成展示章节 | 新增 `Research.run()`，证据以「按子问题分组」的章节插入，并参与引用核验；云端分支把证据写入模型 payload |
| 3 | 单轮单查询 | 全流程只有一次 `S.search`，检索词取自知识条目标题 | 规划层拆子问题，支持两轮（首轮 + 锚点驱动的补充轮） |
| 4 | 单端点首个成功即返回 | `ENDPOINT_CHAIN` 顺序降级 | 新增 `Sources.searchMany()`：按问题类型选源、端点间并行、端点内串行，合并多源结果 |
| 5 | 结果字段残缺 | 只采集 title/snippet/url/host | 增加 `date` / `sourceType` / `authors` / `doi` / `excerpt`（600 字）/ `extra` |
| 6 | 相关性过滤形同虚设 | 2-gram 任一命中即通过，无命中返回全部 | 改为词项覆盖率阈值；无命中时只保留前 2 条并标为待核验 |
| 7 | 无去重/排序/跨源验证 | 不存在相关代码 | 三层去重（URL→DOI→标题指纹）、结构化排序、数值冲突检测 |
| 8 | 引用不可验证 | 引用的 `entry.sources` 与本次检索无关 | 引用核验章节：统计可溯源数、比对本地来源、标出待核验项 |
| 9 | 无检索日志 | 只在 `taskStart` 记了 label | `answer.meta.research` + `answer.trace` + `Research.log()` |

### 16.2 问题类型 → 检索策略

| 意图 | 画像 | 来源类型 | 轮数 |
| --- | --- | --- | --- |
| `cosmos` / `knowledge-target` | 机制与原理 | 百科 + 论文 | 2 |
| `intro-target` / `photo-target` | 天体资料 | 百科 + 论文 + 影像 | 2 |
| `event` | 天象 | 百科 | 1 |
| `nova` | 最新进展 | 论文 + 百科（按时间倒序） | 1 |
| `tonight` / `observe-target` / `gear` / `chart` / `system-view` | **本地计算** | 不检索 | 0 |
| `unknown` | 通用 | 百科 + 论文 | 1 |

观测、器材、星图、今晚看什么这四类由本地星历精算，检索既不必要也不更准，因此**完全不发起检索**，省配额也避免引入噪声。

### 16.3 多轮检索的停止条件

| 条件 | 默认 |
| --- | --- |
| 最大轮数 | 2 |
| 单轮最多检索词 | 4 |
| 总调用预算 | 6 次 |
| 总时间预算 | 12s |
| 子问题全部覆盖 | 立即停止（`covered`） |
| 本轮无新增有效结果 | 停止（`noNew`） |
| 无可提取锚点 | 停止（`noAnchor`） |

第二轮检索词由首轮结果中的锚点生成：已知任务/仪器名（JWST、ALMA、EHT 等 40 余项）、年份、高频作者姓氏。只为**尚未覆盖的子问题**生成，避免重复检索同一关键词。

### 16.4 证据排序（不用单一权威分）

```
类型匹配（是否属于所需来源类型）  权重 3
词项覆盖率（问题实词命中比例）    权重 4
有发表时间                       权重 1
有原文链接                       权重 0.5
多源印证（≥2 个端点收录）         权重 1.5
```

各项写入 `evidence.reliability`，在界面上可查。相关性低于阈值（默认 0.18）的条目直接剔除。

**跨语言匹配**：中文问题 + 英文结果是常态。`questionTerms()` 会把英文实体名并入词项，否则覆盖率恒为 0、排序退化成「谁先返回谁在前」。

### 16.5 证据状态与引用核验

每条证据有一个 `status`：

- `supported`：有 URL + 类型匹配，或 ≥2 个源印证
- `pending`：缺 URL、或缺时间且词项覆盖不足 —— 界面标「待核验」，**不作为确定结论的依据**

`verifyCitations()` 产出四项统计（总数 / 含链接 / 含时间 / 可溯源 / 待核验）与三类结论：

- `verified`：证据均带出处
- `partially-verified`：存在待核验项
- `no-evidence` / `no-source-url`：证据不足，明确说明

同时比对本地知识库声明的来源是否在本轮检索中出现，并把「未出现」如实说明为**检索未覆盖 ≠ 来源无效**，不制造「已验证」的假象。

### 16.6 冲突检测

解析证据中的「数值 + 物理量」（质量 / 距离 / 年龄 / 温度），支持 `6.5e9 solar masses`、`8.3 kpc`、`13.8 Gyr` 等写法，归一化到基准单位后，同一子问题下差异 >10% 即标记冲突。

冲突**并列展示**双方数值与出处，不擅自择一。

> 实现要点：正则匹配必须按位置去重。`6.5e9 solar masses` 会同时被「科学计数法」和「数字+单位」两个模式命中（后者错误抓到 `9 solar masses`），不去重会把 6.5e9 和 9 当成冲突。

### 16.7 云端模型看到什么

选择云端来源时，流程改为「先检索取证 → 再生成」：

- `payload.evidence` 传入结构化证据（编号、标题、来源、时间、状态、摘要 ≤300 字）
- system prompt 增加三条硬约束：只能使用清单中存在的编号、不得自行编号、待核验项不得作确定陈述
- 生成后做两道校验：数值是否能在事实层或证据中找到；文中 `[E#]` 是否真实存在（`fakeCitations`）

### 16.8 可观测性

`answer.meta.research` 记录：画像、子问题数、每轮检索词与条数、锚点、停止原因、调用次数、证据数、可溯源数、冲突数、降级说明、耗时。

`Research.log()` 返回最近 10 次检索的完整记录（问题、子问题、每轮查询、原始条数、去重后条数、停止原因、错误分类）。调试日志默认关闭，设 `window.__ASTRUM_RESEARCH_DEBUG = true` 后输出到控制台。

日志不含任何 API key（`Sources.maskKey` 已具备掩码能力）。

### 16.9 测试

| 工具 | 覆盖 | 用法 |
| --- | --- | --- |
| `tools/research-test.js` | 39 项离线（mock）+ 5 项在线 | `node tools/research-test.js [--online]` |
| `tools/selftest.js` | 全功能回归（含 5 项检索链路） | `node tools/selftest.js [file-url]` |

离线用 mock 检索函数，确定性可复现，覆盖：查询词透传、空查询防御、问题分类、子问题拆解、去重、排序剔除无关项、多轮与停止条件、预算上限、零检索、冲突检测、引用核验、章节生成。

在线单独标记，验证真实端点可达、字段采集、多源聚合。

> **环境说明**：本沙箱设置 `https_proxy`，但 Node 内置 fetch（undici）默认不走环境代理，导致 `api.wikimedia.org` / `zh.wikipedia.org` 直连超时（`curl` 走代理可正常返回 200）。因此在线测试用「论文 + 影像」两个可达类型验证多源聚合，百科端点另作可达性区分，不将网络限制误报为端点故障。

### 16.10 不做的事

- 不引入向量检索 / embedding（破坏零依赖）
- 不新增付费数据源
- 不放宽 CSP
- 不允许模型自由生成天文数值（数值仍以本地星历为准）
- 不用单一「域名权威分」判断可信度

### 16.11 第二轮补强（对照原始要求的缺口修复）

第一轮完成后，逐条复核原始要求，发现 6 项未达成，本轮补齐：

| # | 缺口 | 对应要求 | 修复 |
| --- | --- | --- | --- |
| 1 | **答案正文不随证据变化** —— 证据只在下方列表，正文仍是本地知识库表述 | 四「不再只是搜索结果的拼接」 | 新增 `Research.synthesize()` + `synthesis` 章节；`unknown` 意图且有证据时**改写结论** |
| 2 | 知识库外的问题仍答「不在可确证范围内」，即使检索到了资料 | 四「不允许依靠模型自行补齐」的反面 | `applyResearch` 在无 verdict 时补建一个，结论改为「本地未收录，已检索到 N 条」 |
| 3 | 所有时间塞在同一个 `date`，语义混淆 | 四「区分观测时间、论文发表时间、消息公布时间」 | 新增 `dateKind`：`published` / `released` / `edited`，展示层分别标注 |
| 4 | 无版本信息，预印本与正式发表不分 | 三「来源类型与可用的版本信息」 | 新增 `version`：`preprint`（arXiv/DOI 判定）/ `published` |
| 5 | 未提取误差范围 | 三「已知的不确定性或限制」、四「保留必要的误差范围」 | 新增 `uncertainty`：从摘要抽取 ±/error/confidence 原文片段，不改写不换算 |
| 6 | 要求七列的四类测试缺失 | 七 | 新增时间语义、问题结构、无结果不编造、超时处理四组断言 |

#### 证据概览（synthesis）的设计取舍

离线环境下没有可信的自然语言生成能力，硬拼句子就等于编造。因此综合层只做**可被证据直接支持的组织**：

- **覆盖情况**：`覆盖 1/3 个方面`、哪些子问题有证据、哪些没有
- **关键摘录**：直接引用原文（不改写），带证据编号
- **时间跨度**：按发表/发布/编辑**分别**统计，不混为一谈
- **限制说明**：待核验条数、分歧组数、预印本条数、证据是否已过时

需要成段自然语言综合时走云端模型，并只允许它使用本轮证据编号。

#### 结论改写的边界

`unknown` 意图 + 有证据时，结论改为「本地知识库未收录这个问题；已检索到 N 条相关资料」，副标题说明覆盖与缺口。**不替用户下科学结论** —— 具体内容由下方证据章节按子问题给出并附出处。

#### 两个实现细节

1. `composeFallback` 只生成 `boundary`，**没有 `verdict` 章节**。改写逻辑必须处理「无 verdict」的情况，否则静默失效。
2. `dedupe` 的 `mergeInto` 合并时必须让 `date` 与 `dateKind` 一起迁移。只拷 `date` 会把「词条最后编辑」误标成「论文发表」。
3. 缓存 key 升到 `v2`：item 结构变了（新增 `dateKind`/`version`/`uncertainty`），不升版会让 10 分钟内的旧缓存缺字段，时间语义凭空消失。

## 十七、知识库口径与 Scholar 智能体（v1.9）

### 17.1 不再展示知识库条目数量

**改动**：侧栏 `知识 133 条 · 核验 2026-10` → `知识库 · 已核验 2026-10`（`index.html`）。
帮助卡片的「知识库覆盖 70+ 常见问题」也一并去掉数字。

**原因**：条目数量容易被当作能力背书，但决定可信度的是**每条结论的来源、共识等级与核验日期**，而不是条数。数量还会随增删频繁变动，对外暴露只会制造「数字在涨＝更准」的误解。

**设置中的提示**（`app.js` 设置 → 关于 → 知识库口径）：

> 不展示条目数量。条目多少不等于覆盖能力，判断依据是每条结论的来源、共识等级与核验日期 —— 这些信息在答案的「依据」章节逐条标注。知识库未收录的问题，会转由联网检索取证，或明确告知无法确证。

### 17.2 Scholar · 研读（新增智能体）

**定位**：专门负责学术文献这一层，不承担星历、观测条件、星图定位。

| 项 | 内容 |
| --- | --- |
| id / 名称 | `scholar` / Scholar · 研读 |
| 角色 | 文献 · 论文检索与证据评估 |
| 数据源 | OpenAlex、Semantic Scholar（复用现有端点，未新增依赖） |
| 配置项 | 证据门槛（严格/均衡/开放）、回答深度、推断尺度 |

**职责范围**（写入 `core/agents.js` 的 `scope` 字段，并在详情面板渲染）：

1. 检索词构造与术语归一化（中文 → 英文规范名）
2. 原始论文检索与去重，保留 DOI / 作者 / 发表时间
3. 区分预印本与正式发表
4. 标注证据强弱（可溯源 / 待核验）与研究分歧
5. 定位某结论出自哪篇文献

**使用场景**：某机制的物理过程、某参数的最新测量值、某领域是否存在争议、想找原始论文而非二手介绍、「这个数字是哪篇论文测的」。

**不适用**：今晚能否观测、器材选择、实时天象、星图定位 —— 交给 Kepler、Horizon、Orion。也不做无出处的推论。

**已知限制**：只呈现检索到的文献内容，不替论文下判断；无法确认「某段证据是否足以支持某个结论」时标为待核验。

### 17.3 配置如何真实生效（避免成为挂名角色）

`cfg.scholar` 会在 `applyResearch` 中注入 `rec.scholar`，由 `Research.synthesize()` 消费：

| 配置 | 生效方式 |
| --- | --- |
| 证据门槛 = 严格 | 关键摘录**只采纳** `status === 'supported'` 的条目；某方面全是待核验时标记 `strictEmpty` 并在界面写明「按严格门槛未采纳」，不静默省略 |
| 证据门槛 = 均衡 | 可溯源优先，待核验也列出并带徽标（默认） |
| 证据门槛 = 开放 | 全部列出 |
| 回答深度 = 精简/标准/详尽 | 每个子问题展示 1 / 2 / 4 条关键摘录 |

链路追踪（`answer.trace`）只在**真的检索到论文**时记录 Scholar 的一步：
`N 篇论文 · M 篇有 DOI · K 篇预印本 · 可溯源 J 篇`。没拿到论文就不出场，不空跑。

### 17.4 详情面板

内置智能体现在支持三个新增字段的渲染：

- `scope` → 职责范围
- `useCases` → 使用场景
- `limits` → 已知限制

目的：让「这个智能体能干什么、不能干什么」在界面上直接可读，而不是只给一句简介让人猜。

## 十九、免密钥模型接入（v2.1）

### 19.1 先说清「免费」的两种含义

| 含义 | 例子 | 代价 |
| --- | --- | --- |
| **不花钱** | 免费额度、设备端推理 | 有速率/硬件限制 |
| **不用用户填 key** | Chrome 内置 AI、本地模型服务 | 需要设备能力或本地安装 |

本项目是纯静态前端、无后端，所以**不能**把某个平台的免费额度 key 写进代码——静态站点没有秘密，key 会被扫走并滥用。因此只接「结构上不需要密钥」的两类。

### 19.2 已接入：设备端模型（Chrome 内置 AI）

| 项 | 内容 |
| --- | --- |
| 来源 id | `chrome-ai` |
| 类型 | `device`（新增的第三种类型） |
| 模型 | 浏览器自带的 Gemini Nano |
| 密钥 | 不需要 |
| 网络 | 不需要（本机推理，文本不出设备） |
| 前置条件 | Chrome 148+ 桌面版、约 22 GB 可用磁盘、4 GB 显存 |

实现要点：

- `hasDeviceAI()` 判断 `typeof LanguageModel !== 'undefined'`
- `probeDevice()` 调 `LanguageModel.availability()`，把 `available / downloadable / downloading / unavailable` 映射成中文状态写入 `state.status`
- `generateDevice()` 用 `LanguageModel.create({ initialPrompts: [system] })` + `session.prompt(user)`，复用了原有的 `sysPrompt/userPrompt`，与云端同一套提示约束
- 失败分类：`unavailable` → 硬件不满足；非 `available` → 需先下载；`user gesture` → 提示重新点击

界面上新增中间分组「本机模型 · 免密钥 · 不出设备」，与「本地策略」「云端模型」并列。

**已知限制（写进来源卡的 `note`）**：官方多语言列表为 en/es/ja/de/fr，**暂不含中文**，中文输出质量可能不稳定。这一点必须让用户看见。

### 19.3 已修复：本地模型服务（Ollama / LM Studio / vLLM）

**这是一个真实 bug**：`custom` 来源的配置说明写着「若无需鉴权可留空」，但代码里三处硬性要求密钥（`statusOf` / `test` / `generate`），导致免密钥的本地端点根本用不了。

修复：

```js
function needsKey(base) {
  if (!base) return true;
  if (base.type === 'local' || base.type === 'web' || base.type === 'device') return false;
  if (base.keyOptional) return false;
  return true;
}
```

`custom` 注册项加 `keyOptional: true`，其余云端 provider 仍强制密钥。

配套改动：CSP 的 `connect-src` 增加 `http://localhost:* http://127.0.0.1:* https://localhost:* https://127.0.0.1:*`，否则浏览器会拦截对本地端口的请求。

验证方式：起一个本地 HTTP 服务模拟 Ollama 的 `POST /v1/chat/completions`，密钥留空调用 → 成功返回，服务端收到 `Authorization: Bearer`（空值），说明请求确实发出去了，且不再被密钥校验拦住。

评估过但没接。它的模式是「开发者零成本 + 终端用户登录 Puter 账号付费」，技术上可行，但：

- 需要用户注册并登录第三方账号（多一道门槛）

对一个强调「离线优先、事实可追溯」的工具来说，这套取舍不合适。文档保留结论，供以后需要时参考。

| 把 Gemini / Groq / Cloudflare 免费额度的 key 硬编码进页面 | 静态站点无法保密，key 会被抓取滥用，且违背「用户自己的密钥自己管」 |

## 二十、附件上传（v2.2）

### 20.1 设计取舍：接受任意类型，但如实说明解析到什么

「上传文件」的做法有两种：假装什么都能读，或者按类型如实处理。选后者。

| 类型 | 处理 | 界面标注 |
| --- | --- | --- |
| 图片 png/jpg/webp/gif/bmp | 本机生成缩略图；若来源支持视觉则作为多模态输入 | 「图片」+ 尺寸 |
| 文本 txt/md/csv/tsv/json/log/py… | 读取前 12000 字 | 「文本」+ 已读字数 |
| **FITS** .fits/.fit/.fts | 解析头信息（目标、赤经赤纬、曝光、望远镜、滤镜、尺寸、位深） | 「FITS · 含坐标」 |
| 其余二进制 | **不解析**，只记录名称/大小/类型 | 「该类型暂不解析，仅作记录」 |

关键原则：**不谎称能读懂**。`.raw`、`.zip`、`.exe` 之类不会被「解析成功」，而是明确标注未解析。

### 20.2 FITS 头解析（本项目最有价值的一块）

FITS 是天文观测的事实标准，头信息里就有目标名与坐标。纯文本层面即可读取，不需要解码像素：

- 校验 `SIMPLE = T`
- 按 2880 字节块、每块 36 张 80 字符卡片读取，遇到 `END` 停
- 关键字取 1–8 位，值在 `=` 之后；字符串去引号，数值转 number，`/` 之后视为注释
- `RA`（`HH:MM:SS.S` 或 `HH MM SS.S`）→ 小时；`DEC`（`DD:MM:SS`）→ 度

实测（构造 M42 头）：`RA 05:35:17.3 → 5.588 h`、`DEC -05:23:28 → -5.391°`，与 M42 真实坐标一致。

解出坐标后会**直接生成星图定位入口**（复用既有 `mapref` 章节），点一下就能在实时星图里看这个目标 —— 这是把「上传文件」接进产品主链路，而不是停在展示层。

### 20.3 附件必须参与答案，不能只做展示

第一版只把附件列成一个章节，结果问「这张照片拍的是什么」，答案却在讲今晚的火星 —— 附件被无视了。

修复：`attachHints()` 从附件里提强信号并**并入解析用查询**（不是展示用问题）：

- FITS 的 `OBJECT`
- 文本里的 `目标/对象/天体/object/target: xxx` 行

```js
var hints = attachHints(atts);
var qForAns = hints.length ? (q + ' ' + hints.join(' ')) : q;
ans = AC.buildAnswer(qForAns, ctx, cfgRun);
ans.query = q;   // 对外仍是原问题
```

修复后同一问题答的是「距离地球最近的巨型恒星形成区之一，位于猎户座佩剑中部」——即 M42 本身。

只取强信号、最多两个，避免把整段文本塞进查询污染意图判定。

### 20.4 多模态：只发给真正支持的来源

`vision: true` 只标在 **OpenAI / Anthropic / Gemini / Chrome 内置**四家。其余（DeepSeek、Moonshot、智谱、通义、Mistral、Groq、xAI、自定义）默认不发图 —— 发过去多半 400，不如提前拦下。

界面会明说：

> 当前来源「xxx」不支持图像输入，图片只在本机预览，未发送给模型。如需让模型看图，请切换到 OpenAI / Anthropic / Gemini 或本机 Chrome 内置。

请求体按各家格式拼接：OpenAI 用 `image_url`（dataURL）、Anthropic 用 `source.base64`、Gemini 用 `inline_data`、Chrome 内置用 `Blob`（`atob` 手工解码，不走 fetch 以免受 `connect-src` 限制）。

### 20.5 入口与限制

三种添加方式：**按钮选择 / 拖拽到输入框 / 粘贴**（`clipboardData.files`）。

| 限制 | 值 | 原因 |
| --- | --- | --- |
| 附件数 | 8 | 避免一次塞太多 |
| 文本读取 | 12000 字/文件 | 内存与提示长度 |
| 送模型文本 | 4000 字/文件 | 控制 token |
| FITS 读取 | 28800 字节（10 块） | 头信息足够，不碰像素 |
| 图片 | 6 MB | 超过则只记录信息不预览 |

隐私边界写在输入区下方：**附件只在本机解析**。只有选择云端模型时，文本摘要或图片才随请求发出。

## 二十一、GitHub Pages 部署（v2.3）

### 21.1 为什么选纯静态部署，而不是加后端代理

之前排查出「检索全挂」的根因是 **WorkBuddy 预览服务注入的响应头 CSP**（`connect-src` 只含 `'self'`、本地回环与腾讯系域名）。响应头 CSP 与 meta CSP 取交集，导致 meta 放行的数据源全部失效。

关键结论：**这是宿主环境的限制，不是应用的问题**。GitHub Pages 的两个特性正好避开它：

| 特性 | 影响 |
| --- | --- |
| 只提供静态文件 | 无法跑后端 → 不需要后端 |
| **不注入 CSP 响应头** | 页面里那份 meta CSP 成为唯一策略，白名单直接生效 |

因此不需要引入代理服务，也就保住了「纯静态、双击即用、零依赖」的定位。

```
FAIL Semantic Scholar 11ms  ← 匿名共享限流（429），与部署无关
```

4/5 正常，与预览面板内「全部 0–1ms 失败」形成对照，证明根因定位正确。

## 二十二、区分「网络问题 / CORS / CSP 拦截」（v2.4）

### 22.1 问题：三种失败长得一模一样

浏览器把三种完全不同的失败都报成同一个 `TypeError: Failed to fetch`：

| 真实原因 | 应对方式 |
| --- | --- |
| 真断网 / DNS 失败 | 检查网络 |
| 服务端没给 CORS 头（如 OpenAI） | 需要代理 |
| **当前页面的 CSP 拦了**（如宿主预览面板） | 换个打开方式即可，跟网络无关 |

原实现一律显示「网络不可达或被 CORS 拦截（可填写自建代理地址）」。这会把「宿主限制」误导成「你需要搭一个代理」——用户照着做也解决不了。

### 22.2 修法：用 securitypolicyviolation 拿真实原因

```js
document.addEventListener('securitypolicyviolation', function (e) {
  CSP_HITS[new URL(e.blockedURI).host] = Date.now();
  CSP_LAST = { host, directive: e.effectiveDirective };
}, true);
```

判定时按「同域名 + 时间贴近」匹配，命中即说明这次失败由 CSP 造成，并带上具体指令与域名：

> 被当前页面的 CSP 拦截（connect-src 不允许连 open.bigmodel.cn）· 请在独立浏览器标签打开本站

### 22.3 一个必须注意的时序坑

`securitypolicyviolation` **比 `fetch` 的 rejection 晚一个任务触发**。第一版直接在 catch 里同步查 `CSP_HITS`，永远查不到，结果仍然落到「CORS」分支。

修法：只在「瞬间失败」的路径上让出一小段（80ms）再判定；超时、HTTP 错误等真实耗时路径不等待。

```js
if (!looksLikeFetchFailure(raw)) { /* 直接按原错误处理 */ }
return defer(80, function () { /* 此时才读得到 CSP_HITS */ });
```

### 22.4 顺带确认的事实（有实测支撑）

- **智谱 `open.bigmodel.cn` 支持浏览器直连**：POST 时回显 `Access-Control-Allow-Origin: <你的 Origin>`。所以截图里那次失败与 CORS 无关，纯粹是预览面板的 CSP。
- DeepSeek、Moonshot 同样回显 Origin；通义返回 `*`。
- OpenAI 不发 CORS 头（浏览器直连本来就不被支持），这一家确实需要代理。
- 其余几家因本机代理干扰，探测结果不可靠，**不做断言**。

### 22.5 验证

| 场景 | 修改前 | 修改后 |
| --- | --- | --- |
| 注入 `connect-src 'self'` 后测智谱 | 网络不可达或被 CORS 拦截（可填代理） | 被当前页面的 CSP 拦截（connect-src 不允许连 open.bigmodel.cn）· 请在独立浏览器标签打开本站 |
| 同上，5 个检索端点 | 全部「网络不可达或跨域被拦」 | 全部「被当前页面的 CSP 拦截」 |
| **无 CSP 头的正常环境** | — | 4/5 端点「可用」，**不误判为 CSP** |

回归：research-test 72/72、selftest 35/35、CSP 违规 0。

## 二十三、配置面板的点击丢失（v2.5）

### 23.1 症状

用户反馈「还是无法配置 api」。密钥看起来填进去了，但点「测试连接」毫无反应，状态一直停在「待测试」。

### 23.2 根因：输入框失焦触发重绘，把正要点的按钮换掉

设置面板的每个输入框都挂在 `change` 事件上，而 `change` 在**失焦**时触发。真实操作顺序是：

1. 在密钥框输入 → 光标移到「测试连接」按钮上
2. 按下鼠标 → 输入框失焦 → `change` 触发 → `renderSettings()` **整块重建面板**
3. 抬起鼠标 → 此时按钮已经被替换成新 DOM，点击落在了已脱离文档的旧节点上

实测复现：

```
after-change hasKey=true status=待测试     ← 密钥确实存进去了
stale-btn-still-in-dom=false              ← 按钮被重绘换掉
stale-btn-click-fired=false               ← 那一下点击从未触发
final status=待测试                        ← 测试根本没跑
```

密钥没问题、网络没问题、CSP 也不是这次的原因 —— 是那次点击被界面吃掉了。

### 23.3 修法：就地更新，不整块重绘

`key` 输入框改为只更新自己的 placeholder 与「清除」按钮的可用状态；`model` / `endpoint` / `temperature` / `maxTokens` 同类问题，一律去掉 `change` 后的 `renderSettings()`（它们的 UI 本来就不需要重绘）。

「清除」按钮改为常驻、按 `conf.key` 切换禁用态，避免「保存后要重绘才能出现」这一依赖。

修复后同一脚本：

```
stale-btn-still-in-dom=true
stale-btn-click-fired=true
final status=网络不可达…（测试真的跑完了，不再是「待测试」）
```

### 23.4 顺带纠正的误导文案

原 `KEY_NOTE` 写「浏览器直连云端常受 CORS 限制，如遇失败请填写自建代理地址」，会把人引去搭一个基本不需要的代理。按实测改写：

> 智谱、DeepSeek、Moonshot、通义等支持浏览器直连，可直接使用；OpenAI 等不提供 CORS 的服务才需要自建代理地址。若提示「被当前页面的 CSP 拦截」，说明宿主限制了外连，请换独立浏览器标签打开本站。

帮助文案里同类的「提示 CORS 就换代理」也一并纠正。

### 23.5 回归固化

`tools/selftest.js` 新增 5 项（35 → 40）：

- `config: test button present`
- `config: key saved`
- `config: status no longer 未配置`
- `config: test button survives save` ← 核心回归点
- `config: click still lands after save`

全部通过；`research-test` 77/77、`csptest` 6/6 不受影响。

### 25.2 三个契约（`docs/CONTRACTS.md` + `core/runtime.js`）

**契约一 · 四档应答**：判定依据是「答案怎么来的」，不是「问题是什么」。

| 档 | 判定 | 输出义务 |
| --- | --- | --- |
| 可算 `compute` | 有 rank/observe/visual/mapref 计算章节，或 `meta.computed` | 数值 + 参数 + 模型版本 |
| 可查 `fetch` | 有 web / synthesis 章节 | 数值 + 查询 + 出处 |
| 可释 `infer` | 只有 evidence | 结论 + 出处 + 置信度 |
| 未知 `unknown` | 以上都不成立 | **缺什么 + 去哪拿 + 次优方案** |

生产者可显式声明 `meta.tier`（`classify()` 优先采信），避免「缺口章节本身是 evidence」导致的误判。

**契约二 · 执行记录**：`step()` 升级为可携带 `tool` / `ok` / `check`，旧三参数调用保持兼容。
trace 上显示 ✓（自检通过）/ !（有缺陷）/ ×（失败），`check.detail` 挂 title 供悬停查看。

**契约三 · 数值表示**：`Qty()` / `qtyText()` / `fmtClock()`。
存量代码里大量数值是预格式化字符串，**不强制迁移**——`Qty` 作为新代码原语，旧数据触碰时逐步迁移。

### 25.4 顺带修掉的真 bug：答非所问

`detectIntent` 的兜底分支原文是：

```js

```

实测「光变曲线在哪里下载」被答成火星今晚可见窗口。

改为只认明确的「能看什么」信号，其余如实归入未知档：

```js
if (/能看到|看得到|看什么|有什么可看|值得看|今晚|今夜/.test(text)) return 'tonight';
return 'unknown';
```

## 二十六、问候快车道与检索相关性门槛（v3.1）

### 26.1 问题：一句「你好」跑完了整条天文流水线

用户实测输出：6 步检索 → 4 条无关教育文献 → 调 DeepSeek 生成一段话 → 最后还显示缺口章节。
更糟的是**三个声音互相矛盾**：

| 位置 | 说的是 |
| --- | --- |
| 大标题 | 已检索到 **4 条相关资料** |
| 模型段落 | 检索到的**两条**结果都是教育类文献，**跟天文无关** |
| 缺口章节 | 本地知识库与星表**都没有命中** |

### 26.2 四条根因与修法

| # | 根因 | 修法 |
| --- | --- | --- |
| 1 | 没有「非天文输入」通道，问候语照常走检索 | 新增 `smalltalk` 意图，完全锚定正则，排在所有天文判定之前 |

| 3 | 事实为空仍外发模型，模型只能把缺口说明改写成结论 | `classify() === 'unknown'` 时不调模型，改用确定性文案 |
| 4 | `applyResearch` 无条件覆盖未知结论 | 结果全不可用时保留「未知」，并整体不插入证据章节 |

### 26.3 smalltalk 的边界

正则**完全锚定**（`^...$`），避免误伤：

- ✔ `你好` / `谢谢` / `你是谁` / `你能做什么` / `测试`
- ✘ `你好，今晚能看到什么` —— 有后续内容，不当问候

输出：一句回应 + 三个可点起点。**不检索、不调模型、不显示检索过程、不显示评审章节**。

新增第五档 `chat`（标签「对话」，提示「无需检索」），避免问候被标成「无可靠依据」。

### 26.4 未知档与问候档的分工

| 场景 | 走哪条 | 输出 |
| --- | --- | --- |
| 问候 / 自我介绍 / 测试 | `smalltalk` | 一句回应 + 起点建议，**不解释能力边界** |
| 真天文问题但无依据 | `unknown` | 缺什么 / 去哪拿 / 次优方案 |
| 有依据 | `compute` / `fetch` / `infer` | 正常作答 |

用一个模板套所有情况，是上一版「未收录 + 罗列能力」的根源。

## 二十七、叙述层：把结论与依据合成一段话（v3.2）

### 27.1 问题

之前的答案由各模块的 section 顺序 append 而成——「分块」是流水线的副作用，不是为可读性设计的。
读者要自己把「结论 / 依据 / 证据概览 / 检索证据 / 引用核验 / 边界」拼成一个回答。

### 27.2 为什么不能简单合成一段

| 风险 | 说明 |
| --- | --- |
| 出处断链 | 合成散文后，「1344 光年」与「zh.wikipedia.org」的绑定模糊，学界最在意的可追溯性丢失 |
| 认知地位被抹平 | 本地计算（确定）、外部证据（可能无关）、模型复述（会漂移）三者可信度不同，混在一起就回到了普通聊天机器人的问题 |
| 无法核对 | 引用核验的意义就是验证模型有没有编数字，合成后这个能力消失 |

### 27.3 做法：主叙述整合 + 核对层分离

`renderNarrative(ans)` 把 **verdict + evidence + boundary** 合成一个 `.narr` 块：

```
距离地球最近的巨型恒星形成区之一，位于猎户座「佩剑」中部，肉眼可见为朦胧光斑。

距离 约 1344 光年、直径 约 24 光年、视星等 4.0（肉眼可见）。¹

类型为 H II 区 / 发射星云。

在猎户座腰带下方挂着的那串「小星星」中间，有一团正在孕育年轻恒星的气体云……¹

⚠（边界，如果有）

1  NASA/IPAC Extragalactic Database   本地知识库条目        原文
```

- 数值用 `.nv` 等宽加粗，**嵌在句子里**而不是单独表格
- 出处变成 `<sup class="fn">` 角标 + 脚注行，点「原文」可跳转
- 被消费的 section 不再重复渲染

`renderVerifyStrip(list)` 把 **synthesis / web / citation / conflict** 收进一个 `details.verify-fold`，
标题写「核对 · N 条证据」，默认折叠。

### 27.4 边界条件（哪些不叙述）

| 情况 | 处理 | 原因 |
| --- | --- | --- |
| 含 synthesis / web 章节 | 不叙述 | 证据以引文为主，硬编成散文会丢原文 |
| `tier` 为 unknown / chat | 不叙述 | 没有事实可叙述；缺口三段式与问候需要各自版式 |
| observe / rank / visual / mapref | 保留为独立块 | 它们是表格或画布，编成句子更难读 |
| 结构化章节存在 | **仍叙述**（只接管散文部分） | 早期版本误把这种情况整条排除，导致叙述层几乎永不生效 |

### 27.5 踩到的坑

**① 排他条件写反了**：最初要求「答案不含 observe/rank/visual 才叙述」，而绝大多数天体问题都带观测建议，
结果叙述层几乎从不触发。正确做法是「叙述层只管散文，结构化章节照旧独立」。

**② 测试断言依赖旧结构**：`readability` 断言原本检查 `.kv-data` 存在，叙述层接管后该元素消失。
改为检查 `.narr` / `.narr .nv` / `.narr-fn`。

**③ 叙述层会「吃掉」结论章节**：测试若用 `.sec-verdict` 判断消息就绪会永远等不到。
应扫描「存在 `.narr` 的消息」而不是固定取最后一条。

### 27.6 效果

| 场景 | 改前 | 改后 |
| --- | --- | --- |
| 天体问题 | 结论 + 依据表格 + 观测建议 + 边界（4 块） | **一段话（含角标脚注）** + 观测建议（2 块） |
| 检索答案 | 结论 + 证据概览 + 检索证据 + 引用核验 + 边界（5 块） | 结论 + **核对 · N 条证据**（2 块） |
| 检索全不可用 | 结论 + 一堆无关证据 | 结论 + 缺口三段式 + 一句「未采用」 |

`selftest` **61/61**（新增/改写 5 项叙述层断言）；`research-test` 77/77；`csptest` 6/6。

## 二十八、失败态版式：能答和答不了，不该用同一套排版（v3.3）

### 28.1 问题

答不上来时，页面用了和正常答案同样重的版式：21px 大标题「这个问题我暂时给不出可靠答案」、
带标题线的「缺口与获取路径」区块、`POP · 科普表述` 卡片、`评审结论 · 存在缺口`、
大号琥珀色 `BOUNDARY · 不确定声明` 卡片。

**为了说一句「不知道」，铺了六层。** 而且 `POP · 科普表述` 里写的是我们自己的原则
（「我宁可把缺口说清楚……」）——用户不关心，属于自我表扬式的噪音。

### 28.2 原则

> 正常答案用排版强调结论；答不上来时排版应该退让，只把话说清楚。

### 28.3 改法

| 元素 | 改前 | 改后 |
| --- | --- | --- |
| 结论 | 21px display 大字 | **15px 正文级**、次级色（`.sec-verdict.quiet`） |
| 副标题 | 「下面写清楚缺什么……」 | 空；只有检索失败时才带一句小字说明 |
| 缺口 | `evidence` 章节 + 标题线 + kv 表 + 科普表述卡 | **新 `gap` 章节**：三行、无标题、无卡片、无边框 |
| 科普表述 | 有 | **删除** |
| 评审结论 | 有（「存在缺口」） | **未知档不渲染** |
| 检索未采用 | 大号 BOUNDARY 卡片 | 并入结论副标题的一句小字 |
| 空的核对条 | 显示「核对」但内容为空 | **空章节不生成折叠条** |

新结构：

```
本地没有这个问题的依据。

缺什么   本地没有原始观测数据，也不做图像处理与拟合。
去哪拿   MAST / IRSA / ZTF 归档按坐标检索；星表级别的问题走 SIMBAD 或 VizieR。
我能做   如果你有 FITS 文件，直接拖进来——我能读出目标、坐标、曝光与滤镜。

[今晚适合看什么] [猎户座大星云怎么找] [为什么会有月相变化]
```

### 28.4 顺带修掉的自相矛盾

原来当检索**真的找到可用资料**时，结论会改写成「已检索到 N 条可用资料」，
但 `composeFallback` 留下的 `gap` 章节还挂在下面，于是出现：

> 结论：已检索到 1 条可用资料
> 缺口：本地没有原始观测数据，也不做图像处理

现在：只要 `usableN > 0`，就 `delete ans.meta.tier`（让档位按实际内容重新判定为 `fetch`）
并过滤掉 `gap` 章节。

### 28.5 测试上的教训

这个问题最早被测试「掩盖」了：`contract` 断言在检索找到证据的情况下依然通过，
因为 `gap` 章节残留让「缺什么/去哪拿」照样存在。**断言通过 ≠ 行为正确。**

改为使用不会被检索命中的问法（`zxqvkw 光变曲线原始观测数据在哪下载`），
让失败态断言不依赖网络与来源状态。

`selftest` **64/64**（新增 3 项失败态断言：紧凑三行 / 不用大标题 / 不堆砌卡片）；
`research-test` 77/77；`csptest` 6/6。

## 二十九、A+B+C 三阶段落地（v3.4）

### 29.1 方案 A · 观测决策台

把「答不上来」变成「能算」。

| 新增 | 内容 |
| --- | --- |
| `data/gear.js` | 14 档真实器材（肉眼 / 3 种双筒 / 8 种镜筒 / 2 种镜头），含口径、焦距、焦比与适用场景 |

| `gearfit` 章节 | 参数表 + 逐项自检（✓/!），结论一句话 |

**关键设计：问句里的器材优先于档案设置。**
用户问「M42 用 200/1000 拍得下吗」，必须按 200/1000 算，而不是按他档案里的双筒。
`gearFromText()` 解析四种写法：`200/1000`、`80mm`、`10×50`、`双筒/折射/施卡/马卡`。

实测：

```
M42 用 80mm 能拍吗       → 80mm f/7 · 视场 2.4°×1.6° · 长边 59% / 短边 89% → 能拍，但很紧
M42 用 200/1000 拍得下吗 → 200/1000 · 视场 1.35°×0.89° · 长边 105% / 短边 158% → 装不下
```

判定用「长边比值 + 短边是否裁切」两个量，而不是单一比值——否则 M42 这种长条形目标会被误判成「快出框」。

## 三十、用户消息：复制与重新编辑（v3.5）

### 30.1 触发方式

| 功能 | 入口 | 出现条件 |
| --- | --- | --- |
| 复制 | 气泡下方「复制」 | 鼠标悬停该消息 / 键盘 Tab 聚焦 / 触屏常驻 |
| 重新编辑 | 气泡下方「重新编辑」 | 同上 |

操作条默认 `opacity: 0`，不干扰阅读；`@media (hover: none)` 下常驻，避免触屏无悬停不可达。
两个按钮都是 `<button type="button">`，键盘可达。

### 30.2 交互流程

**复制**

```
点击「复制」
  → 优先同步 execCommand('copy')  ← 不受安全上下文与用户激活限制，反馈即时
  → 失败则 navigator.clipboard.writeText
  → 仍失败则提示「请手动选中」
```

**为什么先 execCommand**：`navigator.clipboard` 在无用户激活（脚本触发、iframe 失焦）时
Promise 既不 resolve 也不 reject，界面会毫无反馈。同步路径能保证一定有结果。
异步路径额外加 800ms 超时兜底，杜绝"点了没反应"。

**重新编辑**

```
点击「重新编辑」
  → 气泡隐藏，就地展开 textarea（预填原文、聚焦、全选）
  → 修改后：Enter 或点「重新发送」
      → 校验通过 → 关闭编辑态 → 旧消息标记「已重新编辑」→ 立即发送新内容
  → Esc 或点「取消」→ 退出编辑态，气泡恢复
textarea 内：Enter 发送 / Shift+Enter 换行 / Esc 取消
```

选**就地编辑**而不是回填输入框：用户能同时看到原文与上下文，改完即发，少两次跳转。

### 30.3 状态反馈

| 场景 | 反馈 |
| --- | --- |
| 复制成功 | 按钮变「已复制」，禁用 1.4 秒后复原 |
| 复制失败 | 按钮变「请手动选中」，同样 1.4 秒复原 |
| 编辑态打开 | 气泡隐藏、textarea 聚焦并全选、边框高亮 + 焦点环 |
| 校验失败 | 操作行右侧出现琥珀色提示文字，输入即清除 |
| 重发成功 | 旧消息操作条左侧显示「已重新编辑」，新消息出现在线程末尾 |
| 重复点击发送 | `fired` 幂等标志，同一次编辑只提交一次 |

### 30.4 边界情况

| 情况 | 处理 | 理由 |
| --- | --- | --- |
| 内容为空 / 纯符号 | 拦截，提示「请输入包含文字或数字的内容」 | 与主输入框同一条校验规则 |
| 超过 `MAX_Q`(200 字) | 拦截并提示缩短，**不静默截断** | 截断会让用户以为发送了原文 |
| 内容未修改 | 拦截，提示「内容没有变化」 | 避免无意义地重跑一次完整流水线 |
| 正在生成答案 | 拦截，提示「正在生成，请稍后再试」 | 与 `ask()` 的 `state.busy` 守卫一致，防止并发 |
| 原消息带附件 | 编辑行提示「原附件不会随重发一起发送」 | 附件已随原消息入库，重发只带文字；必须明说 |
| 重复点击「重新编辑」 | 已有编辑态则直接返回 | 避免叠加多个 textarea |
| 剪贴板 API 不可用 | 回落 execCommand，再回落手动选中 | 兼容 file:// 与权限被拒 |

## 三十一、两处重复逻辑收敛（v3.6）

### 31.1 为什么要做

前面几轮连续暴露同一类问题：**同一条规则在多处各写一遍，改一处漏一处。**

| 重复项 | 出现位置 | 已经造成的后果 |
| --- | --- | --- |
| 输入校验 | `ask()` 与 `startEdit().submit()` | 两套规则并行，编辑框超长时是拒绝、主输入框是截断，语义不一致 |
| 结论句顺序 | `composeTarget` 里 6 个 if/else 分支各拼一次 | 三次同类回归：未收录+罗列能力、未知档改写、结论首句从缺口起头 |

### 31.2 收敛一：`normalizeQuery(raw, opt)`

唯一入口，两个调用方共用清理与「必须含文字或数字」规则，只有超长策略不同：

| 调用方 | 超长策略 | 理由 |
| --- | --- | --- |
| 主输入框 | `truncate` + toast 提示 | 用户正在输入，截断后可立即看到并补全 |
| 重新编辑框 | `reject` + 行内提示 | 用户应自己决定删哪句，静默截断会让人以为发的是原文 |

返回结构 `{ ok, code, text, msg }`，`code` 取 `ok / empty / symbol / truncated / toolong`，
调用方按 `code` 决定提示位置（toast 或行内），不再复制规则。

保留的特殊行为：**只有附件、没有文字**时仍允许发送，用中性默认问题兜底——这一条只在 `ask()` 里判断，
因为编辑框不处理附件。

### 31.3 收敛二：`settleVerdict(head, sub)`

在结论出口拦一次，而不是在 6 个分支各修一次：

```
if (KB_GAP.test(head) && sub && !KB_GAP.test(sub))  → 交换 head 与 sub
```

`KB_GAP` 覆盖：`知识库没有/未收录`、`没有可引用的条目`、`查不到`、`无法确证`。

配套可观测：发生交换时往 trace 写一条「校正结论顺序」，工具名 `verdict-gate`，
这样「门在起作用」这件事本身是可验证的，而不是隐形行为。

**边界**：只有 head 为空时才拿 sub 顶上；head 与 sub 都是缺口语句时保持原样（确实没有可确证内容）。

### 31.4 验证

| 断言 | 结果 |
| --- | --- |
| gate: 缺口在前时被换到副标题 | ✔ `今晚 21:00，月球位于东南…` |
| gate: 缺口降为副标题 | ✔ |
| gate: 正常顺序不被改动 | ✔ |
| gate: 只有缺口时保留原文 | ✔ |

`selftest` **87/87**、`research-test` 77/77、`csptest` 6/6。

### 31.5 仍未收敛的部分

结论句的**生成**仍是各分支自定义（每个分支的措辞与信息量不同，强行统一会丢表达力）。
这一轮只把「顺序」这一条不变量收口。若后续再出现同类问题，下一步应该做的是
把 `head` 拆成 `{claim, basis}` 结构，而不是继续加正则。

## 三十二、技能触发：从「记账」到「能用」（v3.7）

用户选择「推荐」档：联网默认关/可开、技能 A+B、天气随联网开关。本轮只做**决策 2**，因为它零风险、纯本地。

### 32.1 A · 复用上次参数

器材取值优先级改为四层：

```
问句里明说 > 用户档案 > 同类问题的历史技能 > 默认值
```

关键规则：**技能只补空缺**。`GEAR_ID` 一旦设过，就永远压过历史——
否则用户换了器材，系统还按旧参数算，给出的是看起来合理但错误的结论。

复用不是静默的，界面上会显示：


同时往 trace 写一条 `skill-recall` 执行记录，可追溯。

### 32.2 B · 承接上次结论

同意图同目标再次提问时，在答案底部显示一行：

```
↺ 你今天较早时候问过同类问题（共 1 次），上次结论：猎户座大星云 能拍。
```

**边界**：这条只是提示，不参与任何推理，也不被当作依据（`evidence` 里没有它）。
旧结论可能与当前条件不符，所以必须带时间且可忽略。

### 32.3 为什么不做 C（跳过重算）

位置、月相、可见性都随时间变化，命中缓存直接返回等于给出过时结论，而用户无法察觉。
若要加速，只能对**不随时间变化**的量（角径、视场、像元比例）缓存——那属于常量优化，与「技能」无关。

### 32.4 实现要点

`agents` 层不持有 `state`，所以用**注入解析器**的方式拿技能：

```js
AC.setSkillResolver(function (intent, target) { return skillFor(intent, target); });
```

`composeGearFit` 内部通过解析器查询，避免把 UI 状态耦合进编排层。

技能条目结构（`intent|target` 聚合）：

```js
{ key, intent, target, n, at, last, gear }
```

## 三十四、历史对话持久化（v3.9 · 任务 1–7、20）

### 34.1 问题

之前只持久化了配置（设置、器材档案、技能），**对话本身只在 DOM 里**，刷新即丢。
`state.memory` 也只有末 8 轮且仅存内存。

### 34.2 分层

```
UI (app.js)
  ├─ 线程模型 (thread.js)   ← 组织一轮问答
  └─ 存储层 (store.js)      ← 只管存什么、存不下怎么办
```

**核心原则：恢复走「重放 ans」，不存 DOM。** DOM 会随渲染逻辑变化而过期，`ans` 不会。

### 34.3 双后端

| 后端 | 何时用 | 特点 |
| --- | --- | --- |
| IndexedDB | 默认 | 容量大、异步、不阻塞；实测在 file:// 下可用 |
| localStorage | 打开失败 / 超时降级 | 到处能用；自限 2 MB，超限按时间淘汰 |

写入后**回读校验**：配额溢出时 IndexedDB 可能静默失败，
表现为「聊着聊着历史没了」——这比不存更糟。

### 34.4 数据结构

```js
threads  : { id, title, createdAt, updatedAt, schema, count }
messages : { id, threadId, role, at, text, ans?, atts? }
```

每条消息单独 append，不做整线程覆盖写。附件只存缩略图与元信息。

### 34.5 恢复态

`renderAnswer(ans, { restore: true })` 与实时渲染共用同一个函数，但：

| 行为 | 实时 | 恢复 |
| --- | --- | --- |
| 入场动画 | 播 | **禁**（`.msg.restored`） |
| 自动滚动 | 按设置 | **禁** |
| 写入存储 | 写 | **不写**（否则每次刷新都会翻倍） |

### 34.6 清理入口

设置 → 历史记录：显示「本机已保存 N 轮 · 存储后端」，两个按钮
（清空当前对话 / 清空全部历史），均带二次确认。

### 34.7 测试发现的两个真 bug

**① `Thread.init()` 覆盖了并发创建的线程**

boot 的恢复是异步的，可能与首条提问并发。原实现无条件 `cur = t || null`，
会把 `appendUser` 刚创建的线程冲掉，导致 `appendBot` 找不到线程。
现象：线程计数停在 1、bot 消息丢失、测试链悬挂到看门狗。
修复：`if (!cur) cur = t || null;`

**② `navigator.storage.estimate()` 在 headless 下永不 resolve**

`usage()` 直接返回该 Promise，调用方被永远挂住。
修复：加 800ms 超时兜底。

### 34.8 测试工具的两个必备设计

- **`--user-data-dir` 独立配置目录**：否则上一轮写入的 IndexedDB 会被下轮 boot 读回，污染断言。
- **看门狗**：任何一步悬挂都要有结果，否则工具静默失败、只打印 HTML。

## 三十六、数值一致性测试（v4.1 · 任务 21）

### 36.1 为什么需要它

上一轮加了三种身份。身份会改语体与深度，**很容易顺手把事实也改掉**——比如给科普用户写「约 1300 光年」、给研究者写「1344 光年」。一旦发生，产品的可复算承诺就破产了。

这条测试就是这个底线的守门人。

### 36.2 判定方式

不用「集合完全相等」——深度不同，信息量本来就不同（研究者 6 个数、了解模式 3 个数）。

采用**子集 + 容差**：

```
较短答案里的每个数值，必须在较长答案里找到同单位、误差 ≤5% 的对应值
```

为什么允许 5%：语体影响取整（专业 57.3° / 科普 57°），这不是事实冲突。
真正的冲突（1344 → 1500）会远超容差。

### 36.3 排除元信息

抽取数值前先剔除 `.meta-bar`、`.trace-fold`、`.recall`、`.model-note`、`.verify-fold`。
否则置信度、耗时、引用编号都会被当成事实数值，产生大量假失败。

### 36.4 自检：证明测试不是摆设

一个永不失败的测试毫无价值。所以先跑四条比较器自检：

| 自检 | 期望 |
| --- | --- |
| 1344 光年 vs 1500 光年 | 能发现冲突 |
| 1344 vs 1344 | 判为一致 |
| 57.3° vs 57° | 容忍取整 |
| 1344 光年 vs 1344 km | 不同单位不算一致 |

只有自检通过，后面的真实比对才有意义。

### 36.5 结果

```
PASS 自检：能发现数值冲突
PASS 自检：容忍同值
PASS 自检：容忍小幅取整
PASS 自检：不同单位不算一致
PASS 「猎户座大星云是什么」数值跨身份一致   o=2 r=3 l=2
PASS 「M31 能拍得下吗」数值跨身份一致       o=2 r=2 l=2
PASS 「参宿四是什么」数值跨身份一致         o=3 r=6 l=3
```

**7/7**。可以看到研究身份的数值更多（6 vs 3），但短答案的每一个数都能在长答案里找到——
说明差异来自信息量，不是来自事实被改写。

### 36.6 覆盖边界

只验证「跨身份一致」，不验证「数值本身正确」——后者属于事实层，需要外部数据源核对。

## 三十八、任务 22 性能预算：尝试后回退（v4.3）

### 38.1 做了什么

在 `ask()` 起点与 `renderAnswer` 结尾插桩，记录「提问→渲染完成」耗时；
在 `boot()` 结尾记录首屏就绪耗时；通过 `__astrum.budget()` 暴露给测试。

### 38.2 结果：引入回归，撤回

插桩后：

| 套件 | 插桩前 | 插桩后 |
| --- | --- | --- |
| `selftest` | 93/93 | 94/95（`answer=0ms`） |
| `store-test` | 17/17 | 14/15（看门狗） |

**根因**：为了插桩，把 `if (isRestore) … else if (appendBot) …` 这条链改写成了多分支，
结果正常提问时 `appendBot` 被短路——**历史不再落库**。

即使把计时挪成独立语句，`answer` 仍恒为 0，说明插桩点没有按预期执行，
而 store-test 的看门狗同时触发。继续深挖的收益低于风险。

### 38.3 决定：不改生产代码，改在测试侧计时

原则：**为测试而改动生产代码，是拿功能稳定性换测量便利，不划算。**

正确做法是在测试里包住调用：

```js
var t0 = performance.now();
ask(q, function (bot) { var ms = performance.now() - t0; /* 断言 */ });
```

这样生产代码零风险，测量同样准确（甚至更准，因为它测的是端到端）。

### 38.4 本轮结论

- 任务 22 **未完成**，代码已回退到 v4.2 状态，六套件全部恢复绿色。
- 已确认一个真实数据：headless 下首屏脚本就绪约 **2.1–2.4 s**，偏高。
  真正优化应针对启动时的 `warmupSkyModel()` 与全量脚本解析，而不是加计时。
- 下一步若做 22，先做一件更有价值的事：**测出启动耗时构成**，再决定预算。

## 四十、性能预算：重做（v4.5 · 任务 22 完成）

### 40.1 与上一轮的区别

上一轮在**生产代码**里插桩（`ask` / `renderAnswer` / `boot`），把
`if (isRestore) … else if (appendBot)` 链改写坏，导致**正常提问不再落库**，已全部回退。

这一轮改在**测试侧**计时，生产代码一行未动：

```js
var T_READY = performance.now();          // 注入脚本执行时 ≈ 首屏可交互
var t0 = performance.now();
ask(q);
// 答案出现后
var ms = performance.now() - t0;           // 端到端回答耗时
```

好处不只是零风险：它测的是**端到端**（含渲染与落库），比在生产代码里打点更接近用户感受。

### 40.2 预算与实测

| 指标 | 预算 | 实测（headless / file://） |
| --- | --- | --- |
| 首屏脚本就绪 | < 4000 ms | **835 ms** |
| 本地答案渲染 | < 3000 ms | **600 ms** |

两项都有充裕余量。预算取得偏松是有意的：CI 机器与本地性能差异大，
定太紧会变成随机失败，反而训练人忽略红灯。真正的回归（比如某次改动让启动翻倍）
依然会被抓住。

### 40.3 一个观察

上一轮在 `boot()` 内部测到约 2.1–2.4 s，这一轮在注入脚本处测到 835 ms。
两者口径不同（前者包含 boot 内的预热与首屏渲染，后者在脚本执行完毕即刻取值），
不能直接比较。**记录在这里，避免下次看到两个数字时误判为性能提升。**

```js
if (autoStyle && persona 已设 && detected !== persona) {
```

### 41.3 测试上的两个教训

**① DOM 等待型断言在多轮链里不可靠**

给 26 写的首批断言要轮询等 `.recall` 出现，结果与前面用例的并发渲染抢跑，
抛 `Cannot read properties of null`，整条链死掉（无任何输出）。

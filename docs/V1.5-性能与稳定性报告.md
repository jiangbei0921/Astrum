## 2. 并发调度

命令：

```text
node tools/v1-5-concurrency-test.js
```

结果：**17/17**。

| 设定并发 | 实测最大并发 | 16 步耗时 |
|---|---:|---:|
| 1 | 1 | 499 ms |
| 2 | 2 | 250 ms |
| 4 | 4 | 126 ms |
| 8 | 4 | 125 ms |
| 16 | 4 | 126 ms |

结论：

- 产品 Scheduler 硬上限为 **4**（`nextBatch` 中 `Math.min(4, limitParallel)`）；
- 8/16 不会突破 4，符合“根据浏览器实际能力设置合理上限”；
- 依赖步骤严格等待；
- 单步失败不影响无关步骤；
- 取消后未完成步骤标记 aborted；
- 两个任务状态隔离。

未修改 Scheduler 上限：提高并发会增加外部 API 限流/内存压力，且当前基线无证据表明 4 是瓶颈。

## 5. 优化结论

本轮**未**对产品代码做性能重构。原因：

- Router/Planner/PDF/Evidence 的 p95 均在毫秒级；
- Control 本地任务 p95 14.67 ms；
- 并发上限 4 符合现有外部 API 与浏览器资源约束；
- 没有真实基线证明存在需要重构的瓶颈。

只新增了可重复运行的性能/并发/长时测试 harness。后续如出现 P95 明显退化，再按“先基线、后优化、前后对比”的规则处理。

# V2-SKY 子阶段 2C · 纹理分辨率评估报告（512×256 vs 1024×512）

- 日期：2026-11-05
- 结论：**保持 512×256（不建议升级）**，量化依据充分。
- 边界：本阶段只评估，**未升级纹理、未修改 `data/milkyway-bg.js`**（评估前后 SHA-256 均为 `539cd485…6296ad`）。

---

## 1. 评估前提（重要）

原始 NASA SVS 图片本身是 **1024×512**：

| 项 | 值 |
|---|---|
| 文件 | `milkyway_2020_4k_print.jpg` |
| 尺寸 | 1024×512 |
| 体积 | 71,247 B |
| SHA-256 | `1ebe95804f5f0e6e23f77488aaa33fdb4aaef3fd336821fb41b261ddeaee2df0` |
| 许可 | Public domain（NASA SVS Help） |

因此 1024×512 运行时纹理**只是回到源图分辨率，不产生任何超出源图的信息**；而 512×256 是源图 2:1 降采样。两种方案的信息上限都不超过源图 0.352°/px。

---

## 2. 资源体积对比

| 项 | A 512×256 | B 1024×512 | 差值 |
|---|---:|---:|---:|
| 纹理原始字节（RGB565） | 262,144 B | 1,048,576 B | +786,432 B |
| base64 字符数 | 349,528 | 1,398,104 | +1,048,576 |
| `data/milkyway-bg.js` 体积 | 351,028 B（实测现存） | 1,399,604 B（生成实测） | **+1,048,576 B（+1.0 MiB）** |
| standalone `astrum-standalone.html` | 2,367,346 B | 3,415,922 B（估算：现产物 + 增量） | **+1,048,576 B（→ 约 3.26 MiB）** |
| Pages `_site` 总体积 | 2,396,482 B（实测现存） | 3,445,058 B（估算） | **+1,048,576 B** |

- 1024×512 后 standalone 为 **3.26 MiB**，仍在 4 MB 预算内，但余量从 ~43% 收窄到 ~18%。
- 体积增量全部来自 base64 文本，gzip 后增量约 0.6–0.8 MB（未实测压缩，仅作量级参考，不作为结论依据）。

---

## 3. 浏览器实测性能开销

同一页面、真实时钟、各 10 次采样（已预热 3 次）：

| 指标 | 512×256 | 1024×512 | 结论 |
|---|---:|---:|---|
| 解码 `atob` + 字节循环 avg | 2.14 ms | **14.29 ms** | +12.15 ms（约 6.7×） |
| 解码 p50 | 2.0 ms | 14.2 ms | — |
| 解码 p95 | 2.8 ms | 21.0 ms | — |
| 采样 32,768 次（同样的 UV 网格）avg | 0.94 ms | 0.67 ms | 无差异（两者均 <1.5 ms） |
| 采样 p95 | 1.3 ms | 1.0 ms | 无差异 |
| JS 堆（同进程测量） | 9.5 MB | 9.5 MB | 增量被分配时机掩盖，理论常驻 +1.75 MB |

说明：

- 解码成本随 base64 长度近线性增长（4× 数据量 → 6.7× 耗时，含大块内存分配与 GC 压力）。
- **采样成本与纹理边长无关**：天空纹理固定 256×128 = 32,768 次取样，每次只是 O(1) 索引计算。A3 实测 21.2 ms 的绝对主体是每像素一次 `altAzToEq` 反投影（三角函数），不是纹理采样。
- 因此升级到 1024×512 只会增加首帧解码 ~12 ms 与常驻内存 ~1.75 MB，**不会降低天空纹理构建耗时**。

## 4. 采样空间分辨率（关键量化）

| 环节 | 尺寸 | 角分辨率 |
|---|---|---:|
| 源图 | 1024×512 | 0.352°/px |
| **A 运行时纹理** | 512×256 | **0.703°/px** |
| **B 运行时纹理** | 1024×512 | **0.352°/px** |
| **天空纹理（实际采样源）** | 256×128（覆盖 360°/180°） | **1.406°/px** |
| 屏幕栅格 | 160（覆盖整个鱼眼直径） | fov=70° → 0.4375°/px；fov=145° → 0.9063°/px；fov=178° → 1.1125°/px |
| 屏幕像素（Rmax=490） | — | fov=70° → 0.0714°/px；fov=145° → 0.148°/px；fov=178° → 0.1816°/px |

**链条有效分辨率 = 各环节中最差的一环**：

- 512×256 纹理（0.703°/px）已经比天空纹理（1.406°/px）细 **2 倍**；
- 在 fov 145°/178° 的常用广角下，屏幕栅格（0.906/1.113°/px）也比 512 纹理粗；
- 只有在 fov≈70° 时栅格（0.437°/px）才比 512 纹理细，但仍受天空纹理 1.406°/px 限制。

因此把运行时纹理升到 1024×512（0.352°/px）后，**实际采样精度仍被 1.406°/px 的天空纹理卡住**，像素级效果不会有可辨识提升。

## 6. 逐项回答评估重点

**1) 1024×512 是否有实际意义？**
没有。纹理比实际采样源（天空纹理 1.406°/px）细 4 倍，属于过度采样；只增加体积、解码与内存，不增加可见信息。

**2) 当前 160×160 屏幕栅格是否成为新的分辨率瓶颈？**
部分场景是。fov 70° 时栅格 0.437°/px、fov 145° 时 0.906°/px、fov 178° 时 1.113°/px；广角下栅格与天空纹理（1.406°/px）接近，属于同一量级的共同瓶颈。但即使把栅格提到 240，天空纹理 1.406°/px 仍会限制上限。

**3) 是否需要同步提高天空纹理和屏幕栅格？**
如果目标是显著提升银河细节，必须同时提高 **天空纹理**（例如 512×256 → 0.703°/px）与栅格（240），否则任何单点提升都会被 1.406°/px 抵消。代价：天空纹理构建像素数 ×4，按 A3 的 21.2 ms 推算约 **80–85 ms/次重建**，并叠加 250 ms 级去抖后的可见卡顿；栅格 240 约 14 ms。这已超出当前性能预算，**不建议在本阶段或下一阶段默认开启**。

**4) 提高纹理分辨率是否增加不必要的 CPU、内存和体积开销？**
是。CPU：仅首帧解码 +12 ms；内存：纹理常驻 +0.75 MiB、base64 字符串 +1.0 MiB；体积：仓库与发布均 +1.0 MiB。三者均为纯开销，无对应收益。

**5) 当前 512×256 是否已满足现有显示需求？**
是。在 256×128 天空纹理 + 160/128 屏幕栅格的现有链路下，512×256（0.703°/px）已细于下游两级，继续提高运行纹理分辨率不会改变最终画面。

---

## 7. 最终建议

> **保持 512×256。**

依据（量化）：

1. 有效分辨率链为 `纹理 0.703° → 天空纹理 1.406° → 栅格 0.438°–1.113°`，纹理已是最细一环；
2. 升级需 +1,048,576 B 仓库/发布体积、+12.15 ms 首帧解码、+1.75 MB 常驻内存；
3. 采样耗时与纹理边长无关（0.94 vs 0.67 ms），天空构建 21.2 ms 由反投影三角函数决定；
4. 若要真正提升银河锐度，正确顺序是「先天空纹理、再栅格」，且需先做 21 ms 的性能优化，不属于纹理升级本身。

### 若未来确需提升，建议顺序

1. 先优化天空纹理构建（行/列预计算三角函数），把 21.2 ms 降到 ~10–14 ms；
2. 再把天空纹理提到 512×256（0.703°/px）；
3. 最后按需把栅格从 160 提到 192–240；
4. 运行时纹理在以上三项完成后仍可保持 512×256（此时它才重新成为链条最细一环，再考虑是否升 1024×512）。

以上任何一项都需要用户单独授权；本阶段未做任何修改。

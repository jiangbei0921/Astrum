## 4. P0 安全基础核验

### 4.1 A. 身份来源

| 问题 | 结论 | 证据 |
|---|---|---|
| Principal 如何生成 | `Security.makePrincipal()` 从 `ProfileContext.current()` 取 `profileId/sessionId`，其余字段由调用方给出但 agent 必须已注册 | `security.js:153-170` |
| profileId 从哪来 | 只能来自 `Profile.currentId()`（localStorage 当前档案键） | `profile-context.js:12-14`；`profile.js`（P0 审计 §2.1） |
| sessionId 从哪来 | 页面加载时生成一次的模块常量 `s36...`，无 setter | `profile-context.js:10,16-24` |
| 是否存在不可信外部身份输入 | UI/工具参数传入的 `profileId/projectId/principal/sessionId/ownerProfileId` 在工具层被直接拒绝 | `tool-gateway.js:10,49-53` |
| 模型能否控制身份字段 | 不能：身份不进入 Prompt；工具参数含身份字段即 `POLICY_DENIED` | `tool-gateway.js:49-53`；P0 审计 §4.1 |
| 身份上下文能否被任意修改 | `capture()` 返回 `Object.freeze`；`sameSession()` 在每批执行前校验 | `profile-context.js:19-24`；`orchestrator.js:452-460` |

**残留风险（非目标威胁）**：同源脚本/用户在 DevTools 直接修改 localStorage 与 IndexedDB 无法在纯前端防御，P0 已明确列为接受风险（P0 报告 §7）。

### 4.3 C. 数据隔离

| 对象 | 归属字段 | 物理隔离 | 结论 |
|---|---|---|---|
| Thread | 无 `profileId/projectId`；库名按 Profile 命名空间 | IndexedDB `p.<id>.astrum` | Profile 级隔离成立；Project 级不存在 |
| 消息 | 仅 `threadId` | 同库 `messages` 索引 `threadId` | 不跨 Profile；不跨 Project |
| Task | 记录信封有 `ownerProfileId/projectId` | 库名 `p.<id>.astrum.tasks.v1` | Profile 隔离成立；`projectId` 恒 `null`（无调用方传入） |
| TaskState | 无 `profileId/projectId` | 随信封 | P0 审计 C-03；P1 需补 `projectId` |
| TaskStore | `owner` 快照 + 每次读写校验 | 分库 + owner 过滤 | 成立 |
| Evidence | 无归属字段 | 随 TaskState/answer 序列化 | 无独立隔离边界 |
| Claims | 无归属字段 | 同上 | 无独立隔离边界 |
| Report | 无课题归属 | 不持久化 | 无隔离语义 |
| Reducer | 纯函数，无状态 | — | 不涉及 |
| MEMORY | 无归属，页面级单例 | 不持久化 | 跨 Thread 串（P0 已登记） |
| AuditLog | `profileId/projectId` | `p.<id>.astrum.audit.v1` | 成立 |

**关键判定**：P0 之后，「Profile A 读 Profile B」在任务域已被物理阻断；**「Project A 读 Project B」目前无法表达**，因为双方都退化为 `projectId=null`，不存在可区分的边界。这是 P1 必须建立的第一道边界。

| | `planner.js`、`router.js`、`registry.js` | 编排与工具注册 |
| **需扩展** | `task-store.js` | 已接收 `projectId`；需支持按课题查询与恢复校验（索引或过滤） |
| | `task.js` | TaskState 增加可选 `projectId`；提供 checkpoint 写入工具 |
| | `control.js` | 注入 `projectId`；恢复时校验课题归属；写检查点 |

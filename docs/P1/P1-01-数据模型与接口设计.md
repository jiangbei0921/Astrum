# ASTRUM P1 数据模型与接口设计

> 阶段：P1 阶段 A（设计）
> 依据：`docs/architecture/15-架构接口与数据契约统一规范.md`（下称 15）、当前 `core/*.js` 真实实现、P1 任务书 §4.5-§4.10
> 原则：**复用现有契约、只做加法、不做破坏性字段变更**；所有新实体都必须能追溯到 Profile 与 ResearchProject。

---

## 1. 设计总览

```
Profile (profileId)
  └── ResearchProject (projectId)          ← 新增，记忆唯一归属边界
        ├── Thread (threadId, projectId?)  ← 扩展字段，可空
        ├── Task (taskId, projectId?)      ← 复用 TaskStore 信封，可空
        │     └── Checkpoint (checkpointId)← 复用 TaskState.checkpoints
        ├── ResearchMemory (memoryId)      ← 新增，状态机 + 版本/取代
        │     ├── claimIds[] → Claim
        │     └── evidenceIds[] → EvidenceItem
        └── Evidence / Claims / Report     ← 复用现有结构，仅补 projectId 透传
```

四层边界（与任务书 §2.2 一致）：

| 层 | 标识 | 隔离方式 | 现状 |
|---|---|---|---|
| Profile | `profileId` | IndexedDB 库名 `Profile.ns()` | 已实现 |
| ResearchProject | `projectId` | 同一库内 `projectId` 字段 + 存储层 owner/project 校验 | **P1 新建** |
| Thread | `threadId` | `messages.threadId` 索引 | 已有，缺 `projectId` |
| Agent Role | `roleId` | `Security.authorize` 角色策略 | 已有 |

## 2. ResearchProject

### 2.1 字段定义

```js
ResearchProject = {
  projectId:   'prj_<base36-time>_<rand4>',   // 主键，创建后不可改
  profileId:   string,                        // 创建者，来自 ProfileContext，不可由调用方指定
  title:       string,                        // 必填，1..80 字
  description: string,                        // 0..2000 字
  researchGoal: string,                       // 0..1000 字
  researchQuestions: [{                       // 研究问题（有序）
    id: 'q1',
    text: string,
    status: 'open' | 'investigating' | 'answered' | 'dropped'
  }],
  hypotheses: [{ id: 'h1', text: string, status: 'proposed' | 'testing' | 'supported' | 'refuted' }],
  status:      'active' | 'paused' | 'archived' | 'deleted',
  createdAt:   ISO8601,
  updatedAt:   ISO8601,
  archivedAt:  ISO8601 | null,
  deletedAt:   ISO8601 | null,                // 软删除标记
  version:     number,                        // 乐观并发版本，每次写入 +1
  schemaVersion: 1,
  metadata: {
    tags: string[],
    lastThreadId: string | null,
    lastTaskId: string | null,
    memoryCount: number,                      // 派生缓存，可由 memories 重建
    lastActivityAt: ISO8601 | null
  }
}
```

### 2.2 与任务书建议字段的取舍

| 任务书建议 | 采纳 | 说明 |
|---|---|---|
| projectId / profileId | ✅ | 主键与所有者 |
| title / description / researchGoal | ✅ | 必填/可选长度约束见 2.1 |
| researchQuestions / hypotheses | ✅ | 结构化为数组，便于后续记忆/报告引用 |
| status | ✅ | 增加 `deleted` 表示软删除（任务书只给 active/paused/archived，删除语义需显式状态承载） |
| createdAt / updatedAt / archivedAt | ✅ | |
| version | ✅ | 用于乐观并发，避免旧页面覆盖新数据 |
| metadata | ✅ | 只放非权威派生信息，禁止放权限字段 |

### 2.3 生命周期与规则

| 操作 | 允许前置状态 | 结果状态 | 权限 | 规则 |
|---|---|---|---|---|
| 创建 | — | `active` | `project.create`（user） | title 非空；profileId 取自 ProfileContext；同 Profile 可建多个 |
| 编辑 | active / paused / archived | 不变 | `project.update`（user） | `version` 必须匹配，写入后 +1 |
| 暂停 | active | `paused` | `project.update`（user） | 暂停不阻止读取，阻止新增记忆 |
| 恢复 | paused | `active` | `project.update`（user） | |
| 归档 | active / paused | `archived` | `project.archive`（user） | 设置 `archivedAt`；默认不参与召回 |
| 恢复归档 | archived | `paused` | `project.archive`（user） | 不直接回 `active`，避免误触继续写入 |
| 删除确认 | 任意非 deleted | `deleted` | `project.archive`（user，需二次确认输入标题） | 软删除：`deletedAt` 置值，数据保留 |
| 彻底清除 | deleted | 物理删除 | **P1 不提供** | 需单独批准，避免不可逆数据损失 |
| 导出 | 非 deleted | — | `project.read` | 只导出当前 Profile 且 principal 有读权 |
| 导入 | — | `active`（或按文件） | `project.create` | 生成新 ID，见 §8 |

**数据完整性约束**：

1. `profileId` 一经创建不可修改；任何写入必须 `project.profileId === principal.profileId`。
2. 删除课题**不级联删除** Memory / Evidence / Claim：Memory 变为不可召回，Evidence/Claim 保持原样（证据不可因课题删除而消失）。
3. 归档课题可恢复；删除课题在 `deleted` 状态下保留数据，界面只提供「恢复」与「彻底清除（P1 不开放）」。
4. 不同课题之间默认不共享记忆；跨课题引用必须写 `memoryLinks` 记录并经用户授权（见 §7.4）。
5. `version` 冲突时写入失败并返回 `VERSION_CONFLICT`，由 UI 提示刷新，不静默覆盖。

### 2.4 接口契约（`core/research-store.js`）

```js
ResearchStore.create(options) -> store      // options.principal 必须提供（浏览器中）
store.init() -> Promise

// Project
store.createProject(input, principal)            -> Promise<ResearchProject>
store.getProject(projectId, principal)           -> Promise<ResearchProject|null>
store.listProjects(principal, {status, limit})   -> Promise<ResearchProject[]>
store.updateProject(projectId, patch, principal) -> Promise<ResearchProject>   // 校验 version
store.setProjectStatus(projectId, status, principal, {confirmTitle}) -> Promise<ResearchProject>

// Memory
store.putMemory(memory, principal)               -> Promise<ResearchMemory>
store.getMemory(memoryId, principal)             -> Promise<ResearchMemory|null>
store.listMemories(projectId, principal, {status,type,limit,cursor}) -> Promise<ResearchMemory[]>
store.transitionMemory(memoryId, toStatus, principal, detail) -> Promise<ResearchMemory>

// 关联查询
store.listTasks(projectId, principal)            -> Promise<TaskSummary[]>
store.listThreads(projectId, principal)          -> Promise<ThreadMeta[]>

// 导入导出
store.exportProject(projectId, principal)        -> Promise<ProjectBundle>
store.importProject(bundle, principal, opts)     -> Promise<ImportResult>
```

所有方法在**进入存储前**执行：`principal 非空 → Security.ensureSession → Security.authorize → 记录 owner/project 校验 → AuditLog.record`。任一失败返回结构化错误，不抛未捕获异常。

## 3. ResearchMemory

### 3.1 字段定义

```js
ResearchMemory = {
  memoryId:   'mem_<base36-time>_<rand6>',
  profileId:  string,
  projectId:  string,                         // 必填；必须指向未删除课题
  type:       'fact' | 'paper_opinion' | 'calculation' | 'hypothesis'
            | 'experience' | 'research_question' | 'conclusion'
            | 'decision' | 'progress' | 'pending',
  content:    string,                         // 正文，≤4000 字
  summary:    string,                         // ≤200 字，用于召回展示
  source: {
    kind: 'thread' | 'task' | 'paper' | 'calculation' | 'user' | 'import',
    refs: [{ kind, id, uri }]                 // 可追溯引用；thread/task 必须给 id
  },
  sourceThreadId: string | null,
  sourceTaskId:   string | null,
  evidenceIds:    string[],                   // → EvidenceItem.evidenceId
  claimIds:       string[],                    // → Claim.id
  confidence: {                                // 仅供人读，不参与授权/可信判定
    level: 'low' | 'medium' | 'high',
    basis: string
  },
  status: 'draft' | 'proposed' | 'under_review' | 'verified'
        | 'rejected' | 'superseded' | 'archived',
  createdAt: ISO8601,
  updatedAt: ISO8601,
  verifiedAt: ISO8601 | null,
  verifiedBy: 'user' | null,                  // P1 仅允许 user
  version: number,                            // 每次内容/状态变更 +1
  supersedes:   string | null,                // 被本记忆取代的旧 memoryId
  supersededBy: string | null,
  fingerprint: string,                        // 归一化内容哈希，用于去重
  metadata: { tags: string[], originAgent: string | null }
}
```

**裁剪说明**：任务书列出的字段全部保留，但 `confidence` 明确降级为「展示用」，不参与可信判定；未新增 `embedding` 等向量字段（任务书禁止引入向量库）。

### 3.2 记忆类型规则

| type | 允许的 source.kind | 进入 `verified` 的最低条件 |
|---|---|---|
| fact | paper / task / import | 至少 1 个可解析的 `evidenceIds`，且证据 verification 非 `invalid` |
| paper_opinion | paper | 1 个 `evidenceIds` + 1 个 `claimIds`（观点需可定位到原文） |
| calculation | calculation / task | 1 个 `claimIds`，且 Claim 带 `calc` |
| hypothesis | thread / task / user | 用户确认即可，但必须保留 `status` 语义（不得表述为事实） |
| experience | thread / task | 用户确认；不得进入「事实」类展示 |
| research_question | user / thread | 用户确认 |
| conclusion | task / paper | 至少 1 个 `claimIds`，且 Claim 的 support 非空 |
| decision | user / thread | 用户确认并记录决策依据 |
| progress | task / thread | 用户确认 |
| pending | thread / user | 用户确认 |

**硬限制（对应任务书 §4.6）**：

1. 模型只能产生 `draft/proposed`；**任何 Agent 不能把记忆置为 `verified`**。
2. 无 `source.refs` 的 `fact/paper_opinion/calculation/conclusion` 不得进入 `verified`。
3. 重复出现次数不提升可信度；`confidence` 不参与状态判定。
4. 与已 `verified` 记忆冲突且未解决时，只允许 `under_review`，不得直接 `verified`。

### 3.3 状态机

```
draft ──propose──▶ proposed ──submit──▶ under_review ──approve(user)──▶ verified
  ▲                   │                      │
  │                   │                      └──reject(user)──▶ rejected
  └──revise───────────┴──reject(rule)──▶ rejected ──revise──▶ draft

verified ──new evidence contradiction──▶ under_review
verified ──user archive──▶ archived
verified ──new verified memory with supersedes──▶ superseded
archived ──restore(user)──▶ proposed
```

| 转换 | 触发者 | 要求 |
|---|---|---|
| draft → proposed | Agent / 规则提取器 | 必填字段完整、fingerprint 去重 |
| proposed → under_review | 规则引擎 | 引用可解析；无未解决冲突 |
| under_review → verified | **仅 user** | `Security` 授予 `memory.approve`（新增 user 策略） |
| under_review → rejected | user 或规则 | 记录 `reason` |
| verified → superseded | 系统 | 新记忆 `supersedes` 指向旧 ID，且新记忆已 verified |
| verified → under_review | 系统/规则 | 证据更新或出现冲突证据，降级复审 |
| verified → archived | user | 归档后默认不召回 |
| archived → proposed | user | 恢复需重新审核 |

**状态转换日志**：每次转换写 `AuditLog`（`action:'memory.transition'`，`detail:{from,to,reason}`），并在 `metadata` 外单独保留 `history`（不放进 memory 主记录以控体积，见 §6.2 的 `memory_events` store）。

### 3.4 版本与取代

- `version` 每次内容或状态变更 +1；不保留历史正文快照（P1 范围），但保留 `history` 事件。
- 结论被修正时**新建**记录并设置 `supersedes`，旧记录转 `superseded`，不做原地改写——保证来源链可追溯。
- 取代链必须无环；写入前校验 `supersedes` 不存在环。

## 4. Evidence 与 Claims

### 4.1 现状复用

| 项 | 现状 | P1 处理 |
|---|---|---|
| Evidence ID | `evidenceId`，缺省为 `ev_<内容哈希>`（`evidence.js:276-281`） | 直接复用 |
| 来源 | `sourceId/sourceType/uri/title/provenance` | 直接复用 |
| 时间 | `retrievedAt/publishedAt` | 直接复用 |
| 可信状态 | `trust{level,score,basis}` + `verification{state,...}` | 直接复用 |
| Claim 引用 Evidence | `support/contradict: [{eid,strength,basis}]` | 直接复用 |
| Evidence 反向引用 | `claimRefs[]` | 直接复用 |
| 支持/反驳 | `support` / `contradict` | 已支持；**「中性」无字段**，P1 不新增，记录为限制 |
| Claim 版本 | 无 | P1 不新增版本，靠记忆层取代链表达 |

### 4.2 关联规则

1. `ResearchMemory.evidenceIds` 中每一项必须能在当前 Project 的 `EvidenceItem` 集合中解析；解析失败 → 记忆保持 `proposed`，并在导入/完整性检查中报 `DANGLING_EVIDENCE`。
2. `ResearchMemory.claimIds` 同理；Claim 的 `support[].eid` 必须能在 `evidenceIds` 或项目证据集中解析。
3. 完整来源链：`ResearchMemory → Claim → EvidenceItem → Source(uri/sourceId)`，缺任一层不得标记 `verified`（`decision/progress/research_question` 等用户类记忆除外）。
4. 模型生成的文字**不得**被包装为 Evidence：Evidence 只能由 `evidence.js:makeEvidence/fromSourceItem` 从真实来源构造。

### 4.3 课题归属

- `EvidenceItem` 不新增 `projectId`（修改共享契约风险高）；课题归属由使用它的 `ResearchMemory` 与 `Task` 表达。
- `Report` 不新增 `projectId` 到核心结构，而是在 `build()` 的可选入参中透传，输出 `report.projectId`（附加字段，不破坏旧消费者）。

## 5. Thread / Task / Checkpoint

### 5.1 Thread 扩展

```js
Thread = {
  id, title, createdAt, updatedAt, schema: 2, count,
  projectId: string | null      // 新增，可空；空 = 普通对话（兼容旧线程）
}
```

- `Store` 的 `threads` objectStore 结构不变（keyPath `id`），仅多一个字段；旧记录缺省视为 `null`。
- 从课题进入新建 Thread 时写入 `projectId`；旧 Thread 不自动归属任何课题。
- 列表按 `projectId` 过滤在 JS 层完成（线程数量级小，避免 DB 版本升级）。

### 5.2 Task 扩展

- `TaskState` 增加可选 `projectId`（`task.js` 的 `create` 入参）。
- 记录信封已有 `projectId`（`task-store.js:260`），P1 只需让 `create(options)` 的 `projectId` 由 Control 从可信上下文传入。
- **归属校验**：`ownerProfileId` 仍由存储层从 `Profile.currentId()` 决定；`projectId` 必须与 `ResearchStore.getProject()` 返回的 `profileId` 一致后才允许保存。

### 5.3 Checkpoint（复用 15 §4.2 并做加法）

```js
Checkpoint = {
  checkpointId: 'chk_<base36>',        // 新增
  at: ISO8601,
  phase: Phase,
  stepId: string | null,
  inputHash: string,
  stateHash: string,
  budgetUsed: { ms, tokens, llmCalls, searches },
  // P1 追加（全部可空，旧记录不受影响）
  projectId: string | null,
  taskStatus: string,
  version: number,
  memoryIds: string[],
  evidenceIds: string[],
  claimIds: string[]
}
```

写入时机沿用 15 §4.2：PLAN 完成、每个 critical 步骤完成、每次 PROGRESS 决策后；`running` 中间态不写。

## 6. 存储设计

### 6.1 数据库

| 项 | 值 |
|---|---|
| DB 名 | `Profile.ns('astrum.research.v1')`（默认档案 `astrum.research.v1`，其他 `p.<id>.astrum.research.v1`） |
| 版本 | `1` |
| objectStore | `projects`（keyPath `projectId`） |
| | `memories`（keyPath `memoryId`） |
| | `memory_events`（keyPath `eventId`，状态转换/审核记录） |
| 索引 | `memories.projectId`、`memories.projectId_status`（复合 `[projectId,status]`）、`memories.type`、`memories.updatedAt`、`memories.supersedes` |
| | `projects.status`、`projects.updatedAt` |
| 事务 | 单 store 读写；跨 store（project+memory）不放入同一事务，采用「先写主体、后写事件」的补偿顺序 |
| 回退 | IndexedDB → localStorage（键 `Profile.ns('astrum.research.v1')`）→ 内存，语义与 TaskStore 一致 |

**为什么不改 `astrum.tasks.v1` 的版本**：任务库升级会触发全量 onupgradeneeded，风险高于收益。课题查询用 JS 过滤（单档案任务量有限）；如后续需要索引，再单独立项升级 DB 版本。

### 6.2 事件记录

`memory_events` 记录：`create / propose / submit / approve / reject / supersede / archive / restore / import`，字段 `{eventId, memoryId, projectId, profileId, from, to, actorType, actorId, reason, at}`。不记录正文，避免审计日志泄露内容；`AuditLog` 只记录动作与 ID。

### 6.3 升级与迁移

- 新库 `astrum.research.v1` 首次创建，无旧数据迁移。
- `astrum.tasks.v1` 不升级；`projectId` 为新增可选字段，旧记录读为 `null`。
- `threads` 不升级；`projectId` 缺省 `null`。
- 回滚：删除/不加载新模块即可，旧代码不读取新库，不影响既有数据。

## 7. 召回接口（供 P1-04 使用）

### 7.1 请求

```js
RecallRequest = {
  principal,                 // 必填，来自 Security.makePrincipal
  projectId,                 // 必填，来自当前 UI 选择 + 存储校验
  threadId,                  // 当前 Thread，用于排除自身
  query: string,             // 当前用户输入
  budget: { maxItems: 6, maxChars: 2000, maxEvidence: 8 },
  types: string[] | null     // 可选类型过滤
}
```

### 7.2 召回流程（全部在 `research-context.js`）

```
principal 校验（ensureSession）
  → 取 project（ownerProfileId 必须等于 principal.profileId）
  → Security.authorize({action:'read', resource:{resourceType:'memory', ownerProfileId, projectId}})
  → 查询 memories：projectId 匹配 + status ∈ {verified}（默认）
  → 排除 superseded/archived/rejected/draft/proposed/under_review
  → 相关性打分（关键词/实体/类型 + 时间衰减 + 来源可信）
  → 去重（fingerprint、claimIds 重叠）
  → 预算截断（条数 + 字符数，证据单独计数）
  → 附加来源摘要（memoryId, claimIds, evidenceIds, sourceThreadId）
  → AuditLog.record('memory.recall', {count, ids})
```

### 7.3 排序与截断

| 因子 | 权重 | 说明 |
|---|---|---|
| 实体命中 | 0.4 | 与当前问题实体/目标重叠 |
| 类型匹配 | 0.25 | 问题类型 → 记忆类型优先级（事实/结论优先） |
| 时间 | 0.2 | 越新越高；`progress` 权重更高 |
| 来源可信 | 0.15 | 依据 evidence 的 trust/verification |

截断规则：先按条数，再按字符预算；单条记忆超预算时截断 `summary`，不截断 `content` 的来源 ID。

### 7.4 跨课题引用

- 默认禁止。
- 需要时由用户显式创建 `memoryLink {fromProjectId,toProjectId,memoryId,grantedBy,at}`，召回器只读取显式 link，不做同 Profile 自动放开。

## 8. 导入导出

### 8.1 导出包

```js
ProjectBundle = {
  schema: 'astrum.project/1',
  exportedAt: ISO8601,
  project: ResearchProject,
  memories: ResearchMemory[],
  evidence: EvidenceItem[],
  claims: Claim[],
  memoryEvents: MemoryEvent[],
  threads: [{ id, title, createdAt, updatedAt }],   // 仅元数据，不含消息正文（可选导出）
  checkpoints: Checkpoint[],
  manifest: {
    counts: { memories, evidence, claims, threads },
    checksum: 'sha256(canonicalJSON(payload 去掉 checksum))'
  }
}
```

### 8.2 导入规则

| 步骤 | 规则 |
|---|---|
| Schema 校验 | `schema === 'astrum.project/1'`，必填字段与非空约束逐项校验 |
| 权限 | 仅 user 的 `project.create`；目标 profileId 只取当前 ProfileContext，**忽略文件中的 profileId** |
| ID 冲突 | 默认全部重新生成 ID（`prj/mem/ev/claim` 映射表），不覆盖已有记录 |
| 合并 | 可选 `merge` 模式：`fingerprint` 相同则跳过，不覆盖现有 verified |
| 关联校验 | `evidenceIds/claimIds/supersedes` 必须能在包内或目标库解析；失败整体回滚 |
| 信任降级 | **文件中标记 `verified` 的记忆一律导入为 `proposed`**，需重新审核；例外需用户逐条确认 |
| 回滚 | 先在内存校验全部条目，再单事务写入；任一失败清空本批写入（按导入批次 ID 标记） |
| 文件安全 | 拒绝非 JSON、超过 10MB、含可执行字段（`__proto__`, `constructor`）的对象 |

### 8.3 旧数据兼容

- 旧导出包（`schema:1`，仅 threads/messages/settings/skills）继续可导入，路径不变（`app.js importData`）。
- 新包导入不触碰旧线程库；Thread 元数据导入仅用于建立 `projectId` 关联。

---

## 9. 数据完整性检查（`store.verifyProject`）

返回 `{ ok, errors[], warnings[] }`，检查项：

1. 课题存在且 `profileId` 与 principal 一致。
2. 每条 memory 的 `projectId` 指向该课题。
3. `evidenceIds/claimIds` 可解析。
4. `supersedes/supersededBy` 双向一致且无环。
5. `verified` 记忆满足 §3.2 最低条件。
6. 同一 fingerprint 无重复 `verified`。
7. Thread/Task 的 `projectId` 指向存在的课题。

该检查是只读的，供导入后、恢复前、导出前调用。

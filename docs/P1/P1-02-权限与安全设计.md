# ASTRUM P1 权限与安全设计

> 阶段：P1 阶段 A（设计）
> 前提：**不新建身份系统**，全部复用 `profile-context.js`、`security.js`、`tool-gateway.js`、`audit-log.js`、TaskStore 的 owner 校验。
> 核心原则：Profile 隔离优先于 Project，Project 隔离优先于 Thread，Agent Role 决定可访问范围，默认拒绝。

---

## 1. 身份与信任边界

### 1.1 身份来源（复用，不新增）

| 项 | 来源 | 可信性 |
|---|---|---|
| `profileId` | `Profile.currentId()`，经 `ProfileContext.current()` 冻结快照 | 应用内可信；同源脚本篡改 localStorage 为非目标威胁 |
| `sessionId` | 页面加载生成一次，无 setter | 可信 |
| `agentId / roleId` | `Security.resolveRole()`，未注册即拒绝 | 可信 |
| `projectId` | **UI 选择值（不可信）**，进入存储前必须与 `project.profileId` 比对 | 仅作选择器，不作凭证 |
| `taskId / threadId` | 客户端标识，必须配合 owner 校验 | 仅作定位器 |

**关键规则**：`projectId` 是唯一新增的「客户端可传」字段，因此**任何读取都不能只凭 projectId 放行**，必须同时验证课题记录的 `profileId === principal.profileId`。

### 1.2 不可信输入隔离

- 工具参数中的 `profileId/projectId/principal/sessionId/ownerProfileId` 继续由 `tool-gateway.js:10,49-53` 拒绝。
- 导入文件中的 `profileId`、`verified` 状态、`owner` 全部不可信（见 §7）。
- 论文/网页正文中的指令不得改变 principal（P0 已保证：身份不进入 Prompt 路径）。

## 2. 权限资源模型（复用 `Security.authorize`）

### 2.1 资源类型

| resourceType | ID 字段 | owner 字段 | 备注 |
|---|---|---|---|
| `project` | projectId | project.profileId | 新增 |
| `memory` | memoryId | memory.profileId | 新增 |
| `task` | taskId | 记录信封 ownerProfileId | 已有 |
| `thread` | threadId | 库命名空间（Profile） | 已有 |
| `evidence` / `claim` | id | 由所属 project 推导 | 已有能力（只读） |
| `report` | reportId | 由所属 project 推导 | 已有能力（只读） |

### 2.2 新增能力（`security.js` 能力字典变更）

| 能力 | 现值 | P1 目标 | 授权角色 |
|---|---|---|---|
| `project.read` | true | 保持 true | 全员（按 owner/project 校验） |
| `project.create` | false | **true** | user |
| `project.update` | false | **true** | user |
| `project.archive` | false | **true** | user |
| `memory.read` | true | 保持 true | scholar/critic/curator/muse 等（按策略表） |
| `memory.propose` | false | **true** | scholar / curator / critic / muse |
| `memory.approve` | false | **true** | **仅 user**（Agent 策略表不授予） |
| `memory.update` | false | **true** | user（编辑 draft/proposed） |
| `evidence.read` / `claim.read` | true | 保持 | 已有 |
| `evidence.create` / `claim.propose` | false | **保持 false** | P1 不开放 Agent 写证据，避免伪造 |

> 「仅定义能力一律拒绝」的规则（`security.js:262-266`）保持不变；P1 只是把上表明确为已实现，并在代码中落实真实校验。

### 2.3 角色策略调整

| 角色 | 新增能力 | 理由 |
|---|---|---|
| scholar | `memory.propose` | 检索/文献类记忆候选 |
| curator | `memory.propose` | 合并/整理候选 |
| critic | `memory.propose`（仅评审类） | 冲突/反驳记录 |
| muse | `memory.propose` | 综合结论候选；**无 approve** |
| vega/kepler/horizon/orion | 无 | 只读或不涉记忆 |
| lyra/navigator | 无 | 表达层 |
| custom:* | 无（默认拒绝） | P0 行为保持 |

`USER_POLICY` 增加：`project.create/update/archive`、`memory.read/approve/update`、`memory.propose`（用户可手动录入候选）。**不增加 `evidence.create`**。

## 3. 四层隔离矩阵

| 操作 | 同 Profile 同 Project | 同 Profile 跨 Project | 跨 Profile |
|---|---|---|---|
| 列出课题 | ✅ | ✅（仅自己创建的课题） | ❌ 物理不可见（不同库） |
| 读取课题 | ✅ | ✅（README 级元数据不做跨项目开放） | ❌ |
| 读取课题记忆 | ✅（按状态过滤） | ❌ 默认拒绝；显式 link 才允许 | ❌ |
| 写入记忆候选 | ✅（`memory.propose`） | ❌ | ❌ |
| 审核记忆 | ✅（仅 user） | ❌ | ❌ |
| 创建/恢复任务 | ✅ | ❌（projectId 不匹配即 `PROJECT_MISMATCH`） | ❌ |
| 恢复任务 | ✅（重校验） | ❌ | ❌ |
| 读取 Thread | ✅ | 仅当前 Thread；跨 Thread 不自动 | ❌ |
| 导出课题 | ✅ | ❌ | ❌ |
| 导入课题 | 目标只能是当前 Profile | — | ❌（忽略文件 profileId） |
| 查询 Evidence/Claim | ✅（课题内） | ❌ | ❌ |

**Thread 隔离**：Thread 本身不构成科研记忆；跨 Thread 召回只能通过 `research-context.js`，且只召回 `verified` 记忆，不直接读别的 Thread 的消息。

## 4. 统一权限门（唯一入口）

```
所有课题/记忆读写
  → ResearchStore 内部 guard(principal, action, resource)
      → Security.ensureSession(principal)
      → Security.authorize({principal, action, resource:{resourceType, resourceId, ownerProfileId, projectId}})
      → 存储层 owner/project 二次校验（防授权层漏判）
      → AuditLog.record(...)
```

**双层校验**是 P1 的硬要求：
1. 授权层（`Security`）判断角色与能力；
2. 存储层（`ResearchStore`/`TaskStore`）判断记录真实 owner/project。

任何一层失败都拒绝；不允许「授权层放行就跳过存储层校验」。

### 4.1 禁止的绕过路径

| 路径 | 处置 |
|---|---|
| 直接 `indexedDB.open('astrum.research.v1')` | 浏览器同源无法防御，列为非目标威胁；文档与审计记录 |
| 只在前端 UI 隐藏按钮 | 不允许；所有按钮动作必须调用 store 方法 |
| 用 Prompt 要求 Agent 不读其他项目 | 不允许作为控制手段；权限在代码层 |
| `projectId` 仅来自 query/URL | 允许作为选择器，但必须经存储 owner 校验 |
| 内部模块「自己人」调用跳过权限 | 不允许；`ResearchStore` 不接受无 principal 的写操作 |

## 5. 记忆写入与审核权限

| 阶段 | 谁能做 | 代码位置 |
|---|---|---|
| 生成候选（draft） | 任意被授权 Agent / 规则提取器 | `memory.js` 纯函数，不落库 |
| 提交候选（proposed） | `memory.propose` 角色 | `ResearchStore.putMemory` |
| 进入审核（under_review） | 规则引擎（引用完整性通过） | `ResearchStore.transitionMemory` |
| 通过（verified） | **仅 user** | `transitionMemory` 校验 `principal.principalType==='user'` + `memory.approve` |
| 拒绝（rejected） | user / 规则 | 记录 reason |
| 取代（superseded） | 系统 | 仅当新记忆已 verified |
| 归档（archived） | user | `memory.update` |

**Agent 不能自证**：即使 Agent 输出「此结论已验证」，也只能生成 `proposed`；`verified` 必须由用户操作触发。测试需覆盖「Agent 直接调用 transitionMemory('verified') 被拒」。

## 6. 跨 Thread 召回权限

| 检查 | 实现 |
|---|---|
| principal 存在且会话未变 | `Security.ensureSession` |
| 课题属于当前 Profile | `project.profileId === principal.profileId` |
| 角色有 `memory.read` | `Security.authorize` |
| 只读 `verified` | 查询条件 `status==='verified'` |
| 不跨 Project | 查询强制 `projectId` 等值 |
| 不返回其他 Profile | 库命名空间 + profileId 二次过滤 |
| 召回结果审计 | `AuditLog.record('memory.recall')`，只记 ID 与计数 |

**失败行为**：任一检查失败返回空结果 + `denied` 原因，不抛异常、不回退到「全库召回」。

---

## 7. 导入导出权限

| 操作 | 权限 | 附加校验 |
|---|---|---|
| 导出 | `project.read` + owner 校验 | 只导出当前 Profile 的课题；不导出审计日志原文 |
| 导入 | `project.create`（仅 user） | Schema、大小、原型污染、关联完整性、ID 冲突 |
| 导入的记忆 | 一律 `proposed` | 文件中的 `verified` 不采信 |
| 导入的 Evidence/Claim | 保留原始来源字段 | 无法解析的引用 → 整批回滚 |

**跨 Profile 注入防护**：目标 `profileId` 只取 `ProfileContext`；文件内 `profileId` 仅用于提示「来源档案」，不写入新记录。

## 8. 审计要求

| 事件 | action | 必记字段 |
|---|---|---|
| 创建/编辑/暂停/恢复/归档/删除课题 | `project.create/update/archive` | profileId, projectId, decision |
| 提交/审核/拒绝/取代/归档记忆 | `memory.transition` | memoryId, from, to, actorType |
| 召回 | `memory.recall` | projectId, count, memoryIds |
| 建立证据关联 | `memory.link` | memoryId, claimIds, evidenceIds |
| 导入/导出 | `project.import/export` | counts, 结果, 失败原因 |
| 任务恢复 | `task.resume` | taskId, projectId, decision |
| 权限拒绝 | 各 action + `decision:'deny'` | reason（不泄露资源是否存在） |

**日志脱敏**：沿用 `audit-log.js:47-58`，键名命中 `api_key/token/authorization/cookie/secret/password` 直接丢弃；字符串截断 200 字符；只记 ID，不记记忆正文。

**文案要求**：越权统一返回「不存在或不属于当前档案」，不区分「无权访问」与「不存在」，避免存在性泄露（沿用 P0-TASK-008）。

## 9. 越权测试设计（P1 安全用例）

| ID | 场景 | 预期 |
|---|---|---|
| P1-SEC-001 | A 档案读 B 课题 | 不存在/拒绝，审计 deny |
| P1-SEC-002 | 同 Profile 的 Project1 读 Project2 记忆 | 空结果 + deny |
| P1-SEC-003 | 用 projectId 伪造访问他人课题 | 存储层 owner 校验拒绝 |
| P1-SEC-004 | Agent 直接把记忆置 verified | `CAPABILITY_NOT_GRANTED` / `APPROVER_NOT_USER` |
| P1-SEC-005 | scholar 调用 memory.approve | 拒绝 |
| P1-SEC-006 | custom Agent 读课题记忆 | 拒绝 |
| P1-SEC-007 | 召回时 principal 会话已变 | 空结果 `SESSION_CHANGED` |
| P1-SEC-008 | 导入包内 profileId 非当前 | 忽略文件值，写入当前 Profile |
| P1-SEC-009 | 导入包内 verified 记忆 | 落库为 proposed |
| P1-SEC-010 | 工具参数注入 projectId | `POLICY_DENIED` |
| P1-SEC-011 | 恢复任务时课题已归档/删除 | 拒绝恢复并说明 |
| P1-SEC-012 | 越权响应不泄露存在性 | 文案一致 |

## 10. 安全设计待确认

1. `project.read` 是否允许 Agent（非 user）读取课题元数据；当前设计允许 scholar/critic/curator/muse，依据 15 §8.3。
2. `memory.approve` 是否严格限定 `principalType==='user'`；建议是。
3. 是否允许 curator 在无用户在场时「自动归档过期记忆」；建议 P1 不做自动归档。
4. 导入是否允许 `merge` 覆盖同 fingerprint 的 `proposed`；建议只跳过，不覆盖。

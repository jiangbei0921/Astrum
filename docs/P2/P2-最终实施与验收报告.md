## 3. 关键实现约束

1. **无动态代码**：草稿只允许 `executionMode='declarative'`；Schema 扫描并拒绝 `code / script / eval / exec / Function / sourceCode` 及 `__proto__`、`constructor`、`prototype`。
2. **唯一执行出口**：`AstroSkillRuntime.execute` 的每个步骤只调用 `AstroToolGateway.invoke`，不在技能层直接触发工具。
3. **声明 ≠ 授权**：执行权限 = 执行者权限 ∩ Skill 声明 ∩ Profile/Project/Agent/工具作用域；复制或导入技能不会带来新权限。
4. **审批绑定内容**：`approval.versionId + contentHash` 双重校验；审批后修改草稿或版本内容会导致发布失败。
5. **人工门禁**：`approve / publish / rollback` 在 Security 与 Store 双层强制用户身份，任何 Agent 均拒绝。
6. **验证隔离**：验证运行只写 `astrum.skills.validation.v1`；正式库只在审批通过且发布时写入 Publication / published 版本。
7. **版本只增不删**：升级发布旧版本转 `superseded`；回滚只切换指针，新版本转 `rolled_back`，执行历史不重写。
8. **失败分类**：`input / precondition / tool_unavailable / permission / exception / contract / evidence / design / external`；重试最多 2 次，单步超时上限 120s。

## 4. 设计解释（与文档的可核对差异）

以下为实现时需要明确的口径，均未改变文档的安全目标：

1. **改进循环**：`published` 技能通过新版本草稿继续验证时，技能状态保持 `published`，只推进候选版本状态；发布成功后切换 `currentVersionId`。这样避免把正式技能短暂降级为 `draft`，也不允许 `published → draft` 的状态跳变。
2. **验证提交动作**：`validating → pending_approval / validation_failed` 在状态机中由 `system` 执行；Store 允许可信 user/agent 提交，但门禁是库中 Validation 记录（verdict、security 层），不是调用方身份。
3. **SemVer 分类**：`allowedTools` 增加视为权限扩大 → `MAJOR`；仅新增使用既有工具的步骤 → `MINOR`；其余 → `PATCH`。这与 P2-05「权限变化必须 MAJOR」一致。
4. **运行时夹具**：`skill-runtime` 支持 `fixtures` 与 `dryRun`，仅用于测试与试运行；正常执行仍全部经 ToolGateway。UI 不伪造验证结果，缺少夹具时由验证器返回失败原因。
5. **发布时工具校验**：发布检查 `allowedTools` 是否全部在 Registry 中；角色级工具能力在执行时求交。审批人为用户，因此不在发布时用用户角色去卡 Agent 工具能力。

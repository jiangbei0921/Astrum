# P2-04 验证与质量评估规范

> 适用范围：Skill 草稿 → 版本发布前的全部验证与评估
> 原则：安全失败独立阻断；模型评价不得影响安全结论；不做无法兑现的沙箱承诺

---

## 1. 验证入口

```
AstroSkillValidator.validate(draft, ctx)
  ctx = { registry, principal, fixtures, suiteVersion:'p2-1', limits }
```

输出唯一 `Validation` 记录，`verdict ∈ {PASS, CONDITIONAL_PASS, FAIL}`；任何一层异常必须降级为 FAIL 并写明原因。

---

## 2. 六层验证

### 2.1 第一层 Schema

检查：
- 必填字段、类型、长度、枚举（P2-01 §3.2）。
- `workflow` 非空、stepId 唯一、`tool` 存在。
- `inputs/outputs` 契约完整（名称、类型、required）。
- SemVer 合法；`schemaVersion===1`。
- `executionMode==='declarative'`；出现 `code/script/eval/Function` 字段直接 FAIL。
- `allowedTools` 全部存在于 Registry；否则 `UNKNOWN_TOOL`。

### 2.2 第二层静态安全

- 是否声明 `security.authorize`、`principal`、`profile`、`policy` 等越权字段 → FAIL。
- 是否含 `eval/Function/setTimeout(string)/new Function` 等文本模式 → FAIL。
- 是否含外部 URL 作为执行指令（非数据参数）→ WARN/FAIL。
- 是否声明未授权工具或要求提升能力 → FAIL。
- 是否含无限循环/无界重试（`retryPolicy.max > 2` 或 `timeoutMs > 120000`）→ FAIL。
- 输出契约是否可能泄露其他 Profile 字段（如 `profileId`、绝对路径）→ WARN。

### 2.3 第三层功能验证

- 使用固定 fixtures（JSON）逐步骤执行；所有外部工具用静态返回替换。
- 断言：步骤全部执行、输出结构符合 `outputs`、失败分支按 `onError` 生效、异常输入安全退出。
- 相同输入执行 2 次，输出结构一致（允许数值误差在 `expected` 容差内）。

### 2.4 第四层回归验证

- 至少 1 个历史成功案例 + 1 个历史失败案例（来自真实 Task 记录，不允许只用模型生成数据）。
- 对比基线：关键字段不得缺失；不得新增未声明输出。
- 无历史案例时，回归层标记 `NOT_APPLICABLE`，整体最高只能 `CONDITIONAL_PASS`。

### 2.5 第五层安全验证

| 用例 | 预期 |
|---|---|
| Profile A 执行 Profile B Skill | DENY |
| Project A 执行 Project B Skill | DENY |
| Agent 权限不足 | DENY |
| allowedTools 越权 | 执行前 DENY |
| Prompt Injection 文本 | 权限/状态不变 |
| 写正式库尝试 | 拒绝 |
| 外部副作用（网络/文件） | 验证环境拒绝 |
| 敏感字段输出 | FAIL |

任一项失败 → `verdict=FAIL`，`blocking.security=true`，禁止进入审批。

### 2.6 第六层稳定性

- 超时：单步超过 `timeoutMs` 终止并记录 `timeout`。
- 重试：最多 2 次；统计区分「执行次数」与「任务成功」。
- 中断/取消：状态 `cancelled`，不写部分成功统计。
- 依赖缺失：工具不可用 → `tool_unavailable`，不得伪装成功。
- 重复执行：同输入重复执行结果结构一致；不产生重复正式记录。

## 3. 质量评估

### 3.1 维度

| 维度 | 取值 | 来源 |
|---|---|---|
| Correctness | 0..1 / null | 功能+回归通过率 |
| Reliability | 0..1 | 超时/重试/失败率 |
| Security | pass/fail | 安全层（阻断项） |
| Reusability | 0..1 | 输入泛化、步骤通用性 |
| Scope | 0..1 | 适用范围明确度、越界用例 |
| Maintainability | 0..1 | 步骤数、契约清晰度 |
| Efficiency | 0..1 | 预计耗时/实际耗时 |
| Traceability | 0..1 | 来源 Task/Memory/Evidence 完整度 |

### 3.2 规则

- 不把加权总分作为唯一发布依据。
- `Security=fail` 一票否决。
- `Traceability=0`（无来源）不得 PASS。
- 模型辅助评价只写 `sources.modelAssist`，不参与安全与最终判定。
- `confidence` 不得当作成功率。

---

## 4. 阻断规则

以下任一成立 → 禁止 `pending_approval`：

1. Schema FAIL。
2. 静态安全 FAIL。
3. 安全层任一用例 FAIL。
4. 缺少必需测试（至少 schema/static/security）。
5. `requiredCapabilities` 超出执行 Agent。
6. `allowedTools` 含未注册工具。
7. 输出契约缺失。
8. `contentHash` 与内容不一致。

`CONDITIONAL_PASS` 必须列出条件；审批者可接受或拒绝，不得自动发布。

---

## 5. PASS 判定

| 条件 | 要求 |
|---|---|
| Schema | PASS |
| Static | PASS |
| Functional | PASS（至少 1 用例） |
| Regression | PASS 或 NOT_APPLICABLE（后者整体降级） |
| Security | PASS（硬性） |
| Stability | PASS（无超时/崩溃） |
| 来源 | 至少 1 个 Task 或 Memory 引用 |

全部满足 → `PASS`；仅回归缺失 → `CONDITIONAL_PASS`；其余 → `FAIL`。

---

## 6. 隔离与环境

- 验证库 `astrum.skills.validation.v1`，不写正式库。
- 工具白名单：仅 `validationSafe:true` 的本地纯函数。
- 外部工具一律使用 fixtures，不发真实网络请求。
- **不宣称沙箱**：这是应用层隔离（命名空间 + 白名单 + 无动态代码），UI 与报告必须使用「隔离验证」而非「安全沙箱」。

---

## 7. 记录要求

`Validation` 至少包含：validationId、skillId、versionId、testSuiteVersion、六层结果、verdict、failureReasons、startedAt/completedAt、durationMs、fixturesHash、logsHash。
`Evaluation` 至少包含：8 维度、来源分类、阻断项、notes。
两者均写审计事件 `skill.validate` / `skill.evaluate`。

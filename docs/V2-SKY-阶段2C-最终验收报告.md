## 4. 纹理升级建议

**保持 512×256。**

| 依据 | 数值 |
|---|---|
| 有效分辨率链 | 纹理 0.703°/px → 天空纹理 **1.406°/px** → 栅格 0.438–1.113°/px |
| 升级到 1024×512 的体积代价 | +1,048,576 B（仓库/发布/standalone 同步） |
| 升级的解码代价 | 2.14 ms → 14.29 ms（+12.15 ms） |
| 升级的采样收益 | 0.94 ms → 0.67 ms（无实际差异；构建成本由反投影决定） |
| 内存代价 | 纹理 +0.75 MiB、base64 字符串 +1.0 MiB |

结论：运行时纹理已是链条最细一环，1024×512 属于过度采样；显著提升锐度必须「先天空纹理、再栅格」，且需先优化 21 ms 构建成本。本阶段未升级、未修改 `data/milkyway-bg.js`（前后 SHA-256 一致：`539cd485…6296ad`）。

## 5. 尚未解决的问题

### 5.1 真实显示帧率未测（DEFERRED）

- headless `--disable-gpu` 下 rAF 被节流且不稳定：静态缓存命中场景（每帧仅 0.8–0.9 ms 绘制）rAF 间隔 p50 仍为 **38.4 ms**，并出现 0.2 ms 与 53.3 ms 的异常间隔；相机漂移场景出现 964 ms 离群。
- 因此 G1/G2 的 87/120 长帧不能解释为 2C 卡顿，也不能用于验收显示帧率。
- 需在用户实机（GPU 合成、真实显示器刷新）人工观察连续拖动是否卡顿；不通过降低标准换取 PASS。

### 5.2 旧测试 `B4.2` 抖动（既有问题，非本阶段引入）

- 现象：4 次运行中 2 次 21/21、2 次 20/21，唯一失败为 `B4.2 拖动改变 yaw | 180 -> 180`。
- 归因：该脚本使用 `--virtual-time-budget`，指针事件同步派发后由 `drawViewer()` 经 rAF 合并绘制，断言读取的是 rAF 绘制后才写回的 `vc._meta.yaw`；虚拟时钟下 rAF 偶尔未在 300 ms 内推进。旁证：同类断言 `B4.1` 输出 `145 -> 145 / zoom 145° -> 129°`，也是 `_meta` 未更新而标签已更新。
- 影响：仅测试观测方式；`app.js` 指针逻辑未改动，2C 未触碰该路径。
- 建议（不在本阶段修改）：断言改为等待 rAF（`await new Promise(r=>requestAnimationFrame(r))`）或读取同步更新的标签值。

### 5.3 坐标量化精度（沿用 2C 既有结论）

- 映射数学精确（往返 4.12e-13），但 512×256 纹理为 0.703°/px，最近邻半像素误差约 0.35°；阶段A 原定 0.02° 在该架构下不可达。
- 本次评估进一步确认真正瓶颈是天空纹理 1.406°/px，而非运行时纹理。

### 5.4 重建帧处于目标边界

- 时间/地点切换的同步重建 p50 28.6–30.6 ms、p95 32.5–34.6 ms，跨运行会略超 33.3 ms；由 150 ms 去抖保护，连续拖动不会每帧支付该成本。

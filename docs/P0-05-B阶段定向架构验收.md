## 1. Compose Adapter 重复执行检查

### 1.1 真实调用链

```text
AstroControl.run(query, ctx, cfg)
  → prepare()
      → AgentCore.resolveTargets + detectIntent
      → AstroRouter.route
      → AstroPlanner.plan（读 Registry 能力表）
      → TaskState PLAN
  → TaskState EXECUTE
  → AstroOrchestrator.runPlan(plan, state)
      → Scheduler.nextBatch
      → Runner.executeOne(step)
          → Registry.get(step.tool)
          → spec.run(args, ctx, spec, cfg)
              → compose.*: ComposeAdapter.compose(args, ctx, cfg)
                  → AgentCore.buildAnswer(args.query, ctx, cfg)
      → state.steps[] 写 result/status/attempt/outputHash
  → ComposeAdapter 仅在无 compose 步骤时 deliver(query)
  → PROGRESS → JUDGE → COMPOSE → DONE/PARTIAL
```

关键代码位置：

| 环节 | 位置 |
|---|---|
| Adapter 只读 `args.query` | `core/compose-adapter.js:16-25` |
| Registry compose 转发 | `core/registry.js:257-262` |
| Runner 调 spec.run | `core/orchestrator.js:191-200` |
| 控制层最终 answer 取值 | `core/control.js:143-150` |
| 旧 buildAnswer 入口 | `core/agents.js:658-706` |

### 1.2 运行时证据（真实任务）

| 任务 | Registry 实际调用 | buildAnswer 次数 | 最终 answer |
|---|---|---:|---|
| `你好`（L1） | 0 | 1（Adapter.deliver） | 旧 answer |
| `请综述一下黑洞研究…`（T-E） | `paper.search`、`evidence.search`、`compose.domain` | 1（compose.domain） | 旧 answer |
| `M42 和 M31 有什么区别`（T-A） | `kb.lookup`、`kepler.ephemeris`（并行）、`compose.target` | 1（compose.target） | 旧 answer |
| `对比木星和土星的视场`（T-D） | `kepler.ephemeris`×2（并行）、`compare.curate` | 1（Adapter.deliver） | 旧 answer |
| 失败任务（bad adapter） | `kb.lookup`、`kepler.ephemeris`、`compose.target`×2（重试） | 0 | 无 |

### 1.3 发现

**P1-1：Plan 执行结果未被最终回答使用。**

- T-A 的 `t1` 结果是 `{ok, targets, names}`，`t2` 结果是 `{ok, records}`；
- compose 步骤参数仅 `{query, intent, from:['t1','t2']}`；
- `ComposeAdapter.compose` 只读取 `args.query`，`intent/from` 完全未使用；
- 因此 `kb.lookup`、`kepler.ephemeris`、`paper.search`、`compare.curate` 的结果都没有进入 answer；
- 最终 answer 由旧 `buildAnswer()` 独立重新生成。

**P1-2：存在等价的重复计算（不是重复调用同一个 Registry 工具）。**

- Registry 的 `kepler.ephemeris` 真正调用 `Astro.altAz/planet/moon/sun`；
- `buildAnswer` 内的 `composeTarget`（`core/agents.js:940`）再次执行 `resolveTargets`、`jdOfCtx`、星历计算；
- 因此同一个数值链被算了两遍。未发现 `compose*` 被调用两次：每个任务只有一次 compose 步骤或一次 Adapter.deliver。
- 搜索类工具当前是占位返回，不会产生真实网络请求，所以暂未出现“重复取数”的网络副作用；一旦接入真实 Research/Sources，重复风险会变成真实开销。

**P1-3 / P2：T-D/T-F 的 Plan 结果完全未进入交付。**

- T-D 的 `compare.curate` 结果 `{ok, items}` 没有被 Adapter 使用；
- T-F 的检索结果同样未被使用；
- Control 在无 compose 时直接 `Adapter.deliver(query)`，等价于用旧链路重新回答。

**结论**：B 阶段当前是“规划/调度/状态更新 + 旧链路交付”的结构闭环，不是“执行结果驱动最终回答”的数据闭环。不得在报告中描述为真实数据闭环。

## 2. Runner 重试机制边界

### 2.1 代码与触发条件

位置：`core/orchestrator.js:146-224`。

| 错误类型 | 是否重试 | 证据 |
|---|---|---|
| 工具抛异常 | 是 | `withTimeout` 将异常转为 `{ok:false, retriable:true}` |
| 超时 | 是 | `withTimeout` 返回 `reason:'timeout', retriable:true` |
| 工具返回 `{ok:false}` 且 `retriable!==false` | 是 | `normalizeResult` |
| 工具返回 `retriable:false` | 否 | 循环内 break |
| 工具不存在 | 否 | 在循环前返回 `tool_missing` |
| 参数非法 | 否 | 在循环前返回 `args_invalid` |
| 依赖缺失 | 否 | 在循环前返回 `deps_missing` |
| 预算不足 | 否 | 在循环前返回 `skipped:budget` |

重试上限 `while (attempts < 2)`，最多两次调用，不存在无限重试。

### 2.2 阶段边界判断

P0-01 冻结设计明确：

- `§4.1 Executor` 权限含“重试 1 次”；
- `§6.3` 写明“单步超时按 `retriable:true` 重试 1 次；仍失败标 failed”。

因此当前实现属于 **基础执行保护**，不是 C 阶段通用重试系统，也没有超出冻结设计。问题在于状态记录，而不是“应否重试”。

### 2.3 发现

**P2-1：`step.attempt` 不是实际尝试次数。**

- `executeOne` 在循环前只 `step.attempt += 1` 一次（`orchestrator.js:146`）；
- 循环内最多调用两次，但 `attempt` 始终记为 1；
- 失败任务探针显示 `compose.target` 被调用 2 次，`step.attempt=1`。

**P2-2：重试没有对应的 Event。**

- 只在首次开始时写 `step.started`（`:148`），重试过程只写 `state.trace.push`（`:205`），没有第二条 `step.started`；
- Event 仍单调且不驱动执行，但无法从 Event 还原“发生了两次尝试”。

**P2-3：未尊重 `spec.idempotent`。**

- 当前任何 `retriable` 失败都可重试；
- `evidence.search`/`paper.search` 标记 `idempotent:false`，未来真实接入后会重复检索；
- 当前是占位工具，暂无实际副作用，但属于潜在 P2。

**状态/Phase**：重试期间 Phase 保持 `EXECUTE`，Step 保持 `running`，没有非法 Phase 转换；最终只写一次 ok/failed。Phase 转换合法，问题仅是 Step/Event 粒度不准确。

## 3. 真实执行闭环检查

### 3.1 五类任务实测

| 类型 | 任务 | Router | Plan | Scheduler | Runner/Registry | 最终 | Phase |
|---|---|---|---|---|---|---|---|
| L1 LEGACY | `你好` | smalltalk/single/L1/legacy | 无 | 无 | 仅 Adapter.deliver → buildAnswer | 旧 answer | DONE |
| 多步骤 | `请综述…最新进展` | cosmos/research/L3 | T-E | t1→t2→t3 串行 | paper.search、evidence.search、compose.domain | 旧 answer | DONE |
| 并行取数 | `M42 和 M31 有什么区别` | knowledge-target/compare/L3 | T-A | t1+t2 同批并行，t3 单批 | kb.lookup、kepler.ephemeris、compose.target | 旧 answer | PARTIAL |
| 含 compose | 同上 / T-E | — | T-A/T-E | compose 单独串行 | compose → buildAnswer | 旧 answer | DONE/PARTIAL |
| 失败 | 同上 + bad adapter | knowledge-target/compare/L3 | T-A | t1/t2 ok，t3 失败 | compose 调用 2 次后失败 | 无 answer | FAILED |

### 3.2 数据传递结论

- Scheduler → Runner：通过 `state.steps` 与 `plan.steps` 明确共享；
- Runner → Registry：`args/ctx/spec/cfg` 真实传递；
- Registry → 后续步骤：**只写入 `state.steps[i].result`，没有传给下一个工具**；
- Compose Adapter：**只接收 `query`，不接收 `state.steps` 或依赖结果**；
- 最终 answer：旧 `buildAnswer` 独立生成，与 Plan 结果无因果关系。

因此“工具返回值传递给后续步骤”“Compose Adapter 使用前面步骤的执行结果”这两项 **未通过**。

### 3.3 Mock 明确标注

- `paper.search`、`evidence.search`、`simbad.tap`、`fits.parse` 当前返回 `{ok:true, items:[], deferred:true}`（`registry.js:248-255`、`:265-267`），不是真实检索；
- T-E 的 t1/t2 标记 `ok`，但实际没有取得证据；
- `compose.*` 与 `kb.lookup`、`kepler.*` 是真实调用；
- 不得把 T-E 的“步骤 ok”解释为“真实研究流程已完成”。

## 4. TaskState 生命周期检查

### 4.1 生命周期

| 项 | 结果 | 证据 |
|---|---|---|
| 创建者 | 仅 `Control.prepare` 创建一次 | `control.js:39` |
| 持有者 | `Control.run` 返回 `state`，由调用方持有 | `control.js:127-180` |
| Planner 是否共享 | 否；Planner 只接收 route/query/targets，返回 Plan；Control 把 Plan 写入 state | `control.js:77-104` |
| Scheduler/Runner 是否共享 | 是；同一 state 作为参数传入 | `control.js:143-146` |
| 是否存在多个 TaskState | 否，控制层仅一处 `T.create` | 全模块检索 |
| Phase 合法转换 | 是 | L1: INIT→UNDERSTAND→ROUTE→LEGACY→DONE；规划: …→PLAN→EXECUTE→PROGRESS→JUDGE→COMPOSE→DONE/PARTIAL；失败: …→JUDGE→FAILED |
| Event 单调 | 是 | 探针中 seq 1..15，连续 |
| Event 是否驱动执行 | 否 | 执行由 `runPlan`/`switch phase` 决定，Event 只追加 |
| 是否混入 answer | 否 | answer 无 `taskState/task`；探针与测试均验证 |
| answer 是否被新模块改写 | 否 | Adapter 只读 `answer.sections/trace/meta` |

### 4.2 依赖关系表述修正

实际代码不是 `Router → Planner → TaskState → Scheduler → Runner` 的线性管道。准确表述应为：

```text
Router → Planner → Control（创建/写入 TaskState）→ Scheduler → Runner
                         ↑
                  TaskState（共享上下文，Scheduler/Runner 读写）
```

TaskState 是共享任务上下文，不是被顺序“经过”的模块。原报告表述属于 P3 文档问题，代码无需重构。

### 4.3 状态记录缺口

- 失败任务中 Step 实际调用两次，但 `attempt=1`、Event 只有一个 started/failed（P2-1/P2-2）；
- T-D/T-F 没有 compose 步骤时，最终 answer 不在 TaskState 中，TaskState 只记录数据步骤；TaskState 与最终 answer 的关联仅存在于 Control 返回值（P2-4）。

## 7. 最小修复建议（仅建议，未实施）

1. **P1-1/P1-2（需负责人裁定）**
   - 若 B 阶段只承诺“控制骨架 + 旧链路交付”，在验收口径中明确降级为“结构闭环”，不宣称数据闭环；
   - 若要求真实数据闭环，最小路径是让 Compose Adapter 接收依赖结果（例如 `args.fromResults`）并定义结果合并口径；这需要 C 阶段设计，不能在 B 阶段直接改 `compose*`。

4. **P2-4**：无 compose 的模板在 Control 中把最终 answer 摘要/引用写入 TaskState 的交付记录（不写 answer）。
5. **P2-5**：Router 目标去重改为最长别名匹配或规范化实体 id，不直接用原始 `resolveTargets` 命中列表。
6. **P2-7**：新增测试纳入 CI 需单独批准；本次不改 workflow。
7. **P3**：修正报告中的依赖关系与套件计数；CI 统计统一为“19 个 step 条目”。

## 8. B 阶段最终验收结论

- **旧系统兼容性：通过。** 未修改 `ask()`、`buildAnswer()`、`compose*`、`toSections()`、`detectIntent()`；366 条旧断言、P0-02 73 条、P0-03 53 条、20 问 0 字节差异全部保持。
- **控制层结构链路：通过。** Router 分流、Planner 7 模板、TaskState 生命周期、Scheduler 依赖/并行边界、Runner/Registry 调用、失败状态转换均有真实运行证据。
- **真实数据闭环：不通过。** Plan 结果未进入最终 answer，Compose Adapter 重新执行旧 `buildAnswer`；T-E 的检索工具为占位。
- **总体**：B 阶段“结构验收”通过，“数据闭环验收”不通过；无 P0 阻断，但存在 2 项 P1。建议负责人裁定是接受“影子执行”阶段性口径，还是将数据闭环列为 C 阶段目标后再验收。

本报告只读完成，未修改任何产品代码、测试、CI 或基线。等待负责人审阅。

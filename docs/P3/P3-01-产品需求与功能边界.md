# P3-01 · 产品需求与功能边界

- 阶段：P3 · 自主科研规划与执行（Autonomous Research Planning & Execution）
- 前置：P0 身份权限、P1 课题与记忆、P2 Skill 生命周期
- 本文件是**阶段 A 设计文档**，不包含任何代码变更

---

## 1. 产品目标

P3 要让 ASTRUM 从「能回答科研问题、能调用工具与 Skill」，升级为：

> 围绕一个科研目标，生成可解释的任务 DAG，在明确的权限、预算与安全边界内受控执行，持续评估进度与证据缺口，并能暂停、恢复、重试、取消，最终产出可追溯的阶段报告。

必须同时满足四个限定词：

1. **可解释**：每一步为什么存在、由谁执行、消耗多少预算、完成条件是什么，都能被用户看到。
2. **可控**：用户能在计划执行前审阅，在执行中暂停/取消，在预算耗尽时被叫停。
3. **可追踪**：每个结论都能回溯到任务、工具/Skill 版本、证据与计算结果。
4. **有边界**：无无限规划、无无限重试、无无限搜索、无后台常驻、无越权调用。

## 2. 用户使用场景

| 编号 | 场景 | 触发 | P3 行为 |
|---|---|---|---|
| S-1 | 简单事实问答 | 「M31 是什么」 | 不进入 P3，走既有 legacy/L1 路径 |
| S-2 | 单目标观测计算 | 「今晚能看到木星吗」 | 走既有模板（T-A/T-B），不生成多步 DAG |
| S-3 | 双目标对比 | 「比较 M31 和 M33」 | 走既有 compare 模板，P3 只增强报告 |
| S-4 | 文献型科研问题 | 「JWST 对早期宇宙星系演化的最新证据」 | P3 生成 3–6 步 DAG：检索 → 证据整理 → 冲突检测 → 综合 |
| S-5 | 需要计算 + 文献的复合科研 | 「用 Gaia 数据核对 M13 的距离测量差异」 | P3 并行分支：外部检索 ∥ 本地星表/计算 → 汇合 → 评审 |
| S-6 | 关联课题的连续研究 | 用户选中 ResearchProject 后提出第二个问题 | P3 读取该项目记忆作为上下文，但不混入其他项目 |
| S-7 | 中断后续跑 | 用户关闭页面后重开，点「续跑」 | P3 从持久化状态恢复，重新校验权限后执行剩余步骤 |
| S-8 | 预算耗尽 | 长任务触达搜索/模型次数上限 | P3 停止调度、保存状态、如实报告已完成与未完成 |
| S-9 | 用户取消 | 执行中点「取消」 | P3 安全中断，未完成步骤标 aborted，不产出伪结论 |

## 3. 功能清单

### 3.1 必须交付（P3 范围）

| ID | 功能 | 验收要点 |
|---|---|---|
| F-01 | 科研目标解析 | 产出 `ResearchGoal`（title/objectives/constraints/context/requestedOutputs）；缺关键条件时提问而非补全 |
| F-02 | 结构化计划 | 产出 `ResearchPlan`（goalId/version/objective/steps/budget/completionCriteria/assumptions/unresolvedQuestions） |
| F-03 | 任务 DAG | 每个 Step 有 id/title/kind/deps/assignedX/input/expectedOutput/permissions/budget/status/critical/retryPolicy/completionCriteria |
| F-04 | DAG 校验 | 依赖存在、无自依赖、无环、无孤立、可达终点、规模上限、并行安全；失败不执行 |
| F-05 | 能力分配 | 按「确定性工具 → 已授权 Agent → 已发布 Skill」解析；缺失能力记录缺口并暂停该任务 |
| F-06 | 受控执行 | 统一执行门面；全部经 `ToolGateway`；未授权/超预算/依赖未满足一律不执行 |
| F-07 | 状态机 | 与 P1 TaskState 统一；新增 `paused`/`waiting_approval` 为可选状态 |
| F-08 | 暂停/恢复/取消/重试 | 暂停停止新任务并安全中断；恢复前重校验 10 项；取消不可复活 |
| F-09 | 检查点 | 记录计划版本、已完成/待执行步骤、当前步骤、输入/状态哈希、预算用量 |
| F-10 | 预算控制 | 时间/步数/并发/LLM 调用/Token/搜索/重试/重规划/恢复次数；区分真实/估算/不可得 |
| F-11 | 进度与证据缺口 | 任务完成度、目标覆盖度、证据完整度、冲突数、必要计算完成度、未决问题数、预算余量 |
| F-12 | 继续执行决策 | `continue / append / replan / pause / complete / stop`，每个动作带理由 |
| F-13 | 阶段报告 | 18 项固定内容；失败与缺口不得隐藏；结论可回溯 |
| F-14 | 项目隔离 | 目标/计划/步骤/检查点/报告全部带 `profileId + projectId` |

### 3.2 明确不做（P3 范围外）

| 不做 | 原因 |
|---|---|
| 后台常驻科研执行 | 纯静态应用，无后端；不得虚假宣传 |
| 无限自主研究循环 | 属 P4；P3 所有循环有硬上限 |
| 自动创建/发布 Skill | 属 P2 门禁；P3 只能建议 |
| 重写 Agent 名册 | 只做分配，不新增 Agent |
| 重写工具/输出/前端 | 只做接入 |
| 新增后端/数据库/向量库/框架 | 任务书 §5.1 明确禁止 |
| ADS/MAST 数据源适配、证据专业化 | 旧 P3 定义，已排除 |
| 跨设备协同、云端任务平台 | 属 P4 |

## 4. 非功能要求

| 类别 | 要求 | 落地约束 |
|---|---|---|
| 性能 | 计划生成 + DAG 校验 < 300ms（无网络）；单批调度无额外循环开销 | 纯函数校验，不引入 LLM 决策 |
| 规模 | 单计划 ≤ 8 步（沿用 `planner.validate` 上限）；并发 ≤ 4（沿用 `budget.parallel`） | 不放大既有上限 |
| 可靠性 | 存储失败不阻断执行；恢复失败必须显式 DENIED，不得静默继续 | 沿用 P1 降级与拒绝语义 |
| 可测试性 | 全部核心逻辑可在 Node 无浏览器环境测试 | 沿用 `tools/*-test.js` 模式 |
| 安全 | 无 `eval`/`new Function`；无动态代码；工具参数禁身份字段 | 沿用网关约束 |
| 兼容 | 不改 `answer.sections/trace/meta` 契约；不改旧测试预期 | 新增字段一律可选 |
| 可解释 | 每个决策返回 `reason`；报告含「计划摘要 + 实际执行」对照 | 不生成模拟进度 |

## 5. P3 与 P2 的边界

| 维度 | P2 负责 | P3 负责 |
|---|---|---|
| Skill 来源 | 提议、草稿、验证、评估、审批、发布、回滚 | 只查询「已验证 + 已发布 + 当前版本 + 作用域匹配」的 Skill |
| Skill 修改 | 唯一合法入口 | **禁止**任何写入；发现缺陷只记录问题/建议 |
| Skill 版本 | 维护 `currentVersionId` 与历史版本 | 执行时记录 `versionId`；版本失效则拒绝执行 |
| 验证证据 | 六层验证结果 | 引用验证结论，不重跑验证 |
| 失败处理 | 版本回滚 | 记录失败、重试该步骤或改走工具路径，不回滚 Skill |

**硬边界：** P3 任何路径都不得调用 `skillStore.publish/approve/rollback/draftFromProposal`；只能调 `getSkill/listSkills/getPublished/getVersion` 与 `SkillRuntime.execute`。

## 6. P3 与 P4 的边界

| P4 候选 | P3 是否涉及 |
|---|---|
| 无限自主研究（无人值守持续探索） | 否 |
| 后台/云端任务队列 | 否 |
| 多用户协作与共享 | 否 |
| 自动外部副作用（发邮件、提交观测申请） | 否 |
| 跨设备同步 | 否 |
| 新证据体系重构 | 否 |

P3 只交付「一次目标 → 一个计划 → 一次受控执行 → 一份阶段报告」的闭环，可重复触发但必须由用户发起。

## 7. 角色与可见性

| 角色 | 可做 | 不可做 |
|---|---|---|
| 用户 | 创建目标、审阅计划、批准执行、暂停/恢复/取消、增加预算、查看报告 | 绕过授权直接调工具 |
| Muse（编排） | 生成计划、调度、汇总 | 审批/发布 Skill；代表用户扩大预算 |
| Scholar/Curator/Kepler 等 | 在其能力范围内执行被分配的步骤 | 自行获取额外权限 |
| Critic | 评审证据与结论 | 修改计划或证据 |
| 系统（system） | 状态推进、检查点 | 无策略，不能执行业务工具 |

P3 的「计划确认」默认策略：**低风险计划自动执行，涉及高成本（L4/联网检索 > 2 次）或重规划时请求用户确认**。该策略在 `P3-04` 细化。

## 8. 成功标准（产品视角）

1. 用户提出一个复合科研目标后，能在 1 屏内看到：计划摘要、每步目的、预计预算、需要的权限。
2. 任何一步失败，用户能看到失败原因、影响范围与后续动作，而不是笼统「出错了」。
3. 关闭页面再打开，能看到任务处于哪个阶段、哪些步骤已完成、是否可以续跑。
4. 报告能回答「用了哪些 Skill/工具/版本、花了多少预算、还缺什么证据」。
5. 任何越权、跨项目、超预算请求都被明确拒绝，并有审计记录。

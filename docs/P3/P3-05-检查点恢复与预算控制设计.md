# P3-05 · 检查点恢复与预算控制设计

- 目标：让长任务可以**安全暂停、精确恢复、避免重复执行、不超预算**
- 依据：P1 `TaskState.checkpoints` + `AstroControl.resume`；P0 预算契约
- 本文件为设计，不含代码变更

## 2. 检查点结构（增量扩展，保持兼容）

```js
Checkpoint = {
  // —— 现有字段，保持不变 ——
  checkpointId, at, phase, stepId, inputHash, stateHash,
  budgetUsed, projectId, taskStatus, version,
  memoryIds[], evidenceIds[], claimIds[],

  // —— P3 新增（全部可选）——
  planId: string | null,
  planVersion: number | null,
  currentStepId: string | null,
  completedStepIds: string[],
  pendingStepIds: string[],
  paused: boolean,
  inputs: [{ stepId, inputHash }],   // 每步输入哈希
  outputs: [{ stepId, outputHash, toolId, toolVersion, skillVersionId }],
  recoveries: number
}
```

**兼容策略：** `schemaVersion` 仍为 `1`；新字段缺失时使用默认值；`TaskState.validate` 不要求这些字段存在。

**存储位置：** 继续放在 `TaskState.checkpoints` 内（随任务落库），不新增独立 store，避免与 P1 导出格式分叉。

## 3. 哈希设计

| 哈希 | 计算 | 用途 |
|---|---|---|
| `inputHash`（每步） | `sha256(canonicalJSON(step.args + depOutputHashes))` | 判断输入是否变化 |
| `outputHash` | 现有：`sha256(canonicalJSON(result))` | 判断结果是否可复用 |
| `stateHash` | 现有：快照哈希 | 判断检查点是否被篡改/损坏 |
| `planHash` | `sha256(canonicalJSON(plan.steps))` | 判断计划版本是否一致 |

`canonicalJSON` 复用 [task.js](file:///D:/Projects/Astrum/core/task.js#L133-L158)，保证稳定排序。

## 4. 结果复用判定

### 4.1 判定表

| 条件 | 结论 |
|---|---|
| step.status ≠ `ok` | 重新执行 |
| 无 `outputHash` 或 `result` | 重新执行 |
| `inputHash` 与当前计算不一致 | 重新执行 |
| 工具版本变化 | 重新执行 |
| Skill `versionId` 变化或不再 published | 重新执行（或改走替代能力） |
| 计划 `planVersion` 变化且该步在新计划中不存在 | 丢弃 |
| 工具 `idempotent === false` | 重新执行（即使输入未变） |
| `ttlMs` 已过期（S1 外部只读） | 重新执行 |
| 以上均通过 | **复用** |

### 4.2 原则

- 仅凭 `status === 'ok'` **不得**直接复用（任务书明确要求）；
- 复用必须在报告中标注 `reused: true` 及复用依据；
- 非幂等步骤永不自动复用。

## 5. 恢复流程

```
resume(taskId, principal)
  │
  ├─ 1. load(): store.getRecord + store.get + authorize(read)
  ├─ 2. authorize(resume) + ensureSession
  ├─ 3. schemaVersion === 1
  ├─ 4. 项目存在且非 archived/deleted
  ├─ 5. 检查点完整性：
  │       - 存在至少一个检查点
  │       - stateHash 可重算一致
  │       - planId/planVersion 与 state.plan 一致
  ├─ 6. 依赖状态重校验：deps 是否仍 ok（失效则标记该步重跑）
  ├─ 7. 能力重校验：工具存在、Skill 仍 published、版本未变
  ├─ 8. 预算重校验：remaining 足够执行至少一个 pending 步骤
  ├─ 9. recoveries < limit.recoveries
  ├─ 10. 结果复用判定（§4）
  ├─ 11. 不可复用步骤重置为 pending；可复用保持 ok
  ├─ 12. running → pending（现有行为）
  ├─ 13. recoveries += 1，记账
  ├─ 14. 事件 task.recovered + 审计
  └─ 15. runPlan（仅调度 pending）
```

### 5.1 拒绝语义（必须显式）

| 情况 | 返回 |
|---|---|
| 非本人任务 | `DENIED`（不泄露存在性） |
| 会话变化 | `DENIED / SESSION_CHANGED` |
| 课题已归档/删除 | `DENIED / PROJECT_NOT_ACTIVE` |
| schema 不兼容 | `DENIED / SCHEMA_INCOMPATIBLE` |
| 检查点缺失/损坏 | `DENIED / CHECKPOINT_INVALID` |
| 恢复次数超限 | `DENIED / RECOVERY_LIMIT` |
| 预算不足 | `DENIED / BUDGET_EXHAUSTED` |
| Skill 已失效 | 该步重跑；无替代 → `blocked` |

**禁止：** 从旧状态无条件继续；静默跳过权限；把暂停中的任务直接标成功。

## 6. 检查点写入时机（P3 增补）

| 时机 | 新增字段 |
|---|---|
| PLAN 后 | planId/planVersion/planHash/pendingStepIds |
| 每个 critical 步骤 ok 后 | completedStepIds/outputs/currentStepId |
| 每个批次结束 | 同上 + budgetUsed |
| 暂停时 | paused=true/currentStepId |
| 恢复前（成功判定后） | recoveries |
| PROGRESS 后 | 全量 |

写入失败**不阻断执行**（现有 `safeCheckpoint` 行为），但必须记录错误事件。

## 7. 预算模型

### 7.1 分档（沿用）

| 档 | ms | tokens | llmCalls | searches | parallel | replans | appends | retries |
|---|---|---|---|---|---|---|---|---|
| L1 | 300 | 0 | 0 | 0 | 1 | 0 | 0 | 0 |
| L2 | 3000 | 1200 | 1 | 1 | 2 | 1 | 1 | 1 |
| L3 | 15000 | 3000 | 2 | 2 | 4 | 2 | 3 | 1 |
| L4 | 120000 | 8000 | 3 | 3 | 4 | 2 | 3 | 1 |

来源：[BUDGET_LIMITS](file:///D:/Projects/Astrum/core/task.js#L41-L46)。

### 7.2 P3 新增预算项

| 字段 | 默认 | 说明 |
|---|---|---|
| `recoveries` | L1:0 / L2:1 / L3:3 / L4:3 | 恢复次数 |
| `maxSteps` | 8 | 与 DAG 校验一致（只读，不消耗） |

新增项必须加入 `BUDGET_FIELDS` 与 `validateBudget`，否则 `spend` 会忽略。

### 7.3 记账规则

| 成本 | 记账时机 | 数据来源 |
|---|---|---|
| `ms` | 每步结束 | 工具 `cost.ms`（声明值） |
| `tokens` | 每次 LLM 工具调用 | 工具 `cost.tokens`（声明值）；如 API 返回真实 usage，优先真实值 |
| `llmCalls` | 每次 `llm.*` 调用 | **新增**（当前未扣减，G-07） |
| `searches` | 每次 `evidence.search` / `paper.search` | 工具 `cost.searches` |
| `replans` | 每次重规划 | 固定 1 |
| `appends` | 每次追加 | 固定 1 |
| `retries` | 每次重试 | 固定 1（或复用 `retries` 计数） |
| `recoveries` | 每次恢复 | 固定 1 |

### 7.4 数据来源分级（不得伪造）

| 级别 | 标记 | 说明 |
|---|---|---|
| `measured` | 真实 | API 返回 usage / 实际耗时 |
| `estimated` | 估算 | 工具声明 `cost` |
| `unavailable` | 不可得 | 无数据时不填精确值，报告显示「不可得」 |

报告与 UI 必须区分三者；不得把估算写成真实。

### 7.5 超预算行为

1. 达到任一上限 → 不再启动新批次；
2. 在飞请求允许完成，结果如实记录；
3. 保存状态 + 检查点；
4. 追加事件 `verdict.issued` / `progress.decided`（action=`stop`, reason=`budget_exhausted`）；
5. 报告列出已用/上限/未完成步骤；
6. **不得自动扩大预算**；增加预算必须用户显式操作并审计。

## 8. 静态部署限制（必须如实声明）

| 事实 | 结论 |
|---|---|
| 纯静态浏览器应用，无常驻进程 | 页面关闭后任务**不在后台执行** |
| 状态存于 IndexedDB | 只是「已保存」，不等于「仍在运行」 |
| 恢复 | 用户重新打开页面 → 读取状态 → 重新校验 → 继续剩余步骤 |
| 暂停 | 只能阻止新批次，不能杀死在飞请求 |
| 取消 | 通过 `AbortController`，尽力中断 |

文档、UI 与报告均不得使用「后台持续运行」「关机后继续」等表述。

---

## 9. 验收要点

1. 检查点字段完整、可重算、哈希一致；
2. 正常暂停 → 状态保存 → 恢复后不重复已完成步骤；
3. 输入变化 → 对应步骤重跑；
4. Skill 版本变化 → 重跑或阻断；
5. 检查点损坏/缺失 → 显式 DENIED；
6. 恢复次数超限 → 拒绝；
7. 预算耗尽 → 停止且报告准确；
8. 页面刷新/重开后恢复可用（Node 侧用 IDB 桩，浏览器侧单列）；
9. 旧任务（无新字段）可恢复。

# P3-06 · 研究进度与证据缺口评估设计

- 目标：判断「当前研究是否达到阶段目标」，并为下一步给出**有理由、有上限**的动作
- 原则：复用 `AstroEvaluator` 与 `Research/Claims/Critic`，不重建证据体系
- 本文件为设计，不含代码变更

---

## 1. 现状

[evaluator.decide](file:///D:/Projects/Astrum/core/evaluator.js#L242-L398) 已实现：

- 输入：`state`、`plan`、`research`（evidence/claims/conflicts/verdicts/differences）、`opts`；
- 前置：取消 → stop；仍有 pending → continue；预算耗尽 → stop；criticalFailed → replan/stop；非研究 → stop；
- 缺口码：`no_evidence`、`critical_claim_without_support`、`critical_claim_not_verified`、`critical_conflict`、`noncritical_conflict`、`insufficient_information` 等；
- 动作：`continue / append / replan / stop`；
- 上限：`appends`、`searches`、每轮只追加 1 条、去重（`appendedKeys`）。

**缺口：** 评估依据是「research 结果」而非「计划完成条件」；没有目标覆盖度；没有 `pause/complete` 显式动作；没有把任务完成度、必要计算完成度纳入。

## 2. 评估模型

### 2.1 六维指标

| 维度 | 计算 | 数据来源 |
|---|---|---|
| 任务完成度 | `settledSteps / totalSteps`（仅参考，不作唯一依据） | `state.steps` |
| 关键目标覆盖度 | `coveredObjectives / mustObjectives` | `goal.objectives` + `plan.completionCriteria` |
| 证据完整度 | `1 - unsupportedRequiredClaims / requiredClaims` | `research.claims` + 证据 |
| 关键冲突数 | `criticalConflictCount` | `research.conflicts` |
| 必要计算完成度 | `okCalcSteps / requiredCalcSteps` | `state.steps`（kepler 类） |
| 未解决问题数 | `plan.unresolvedQuestions + gapCount` | plan + 本轮 gaps |
| 预算余量 | `remaining / limit`（ms/searches/appends） | `state.budget` |

### 2.2 阶段完成判定

满足以下**全部**才可 `complete`：

1. 所有 `must` 目标都有对应 `completionCriteria`；
2. 每条 required criteria 状态为 `met`；
3. 无 `critical_conflict` 未解决；
4. 无 `critical_claim_not_verified`；
5. 无必须执行但未完成的 critical 步骤（失败/blocked）；
6. 预算未耗尽。

否则不得宣称完成。

## 3. 缺口检测

### 3.1 缺口类型

| 代码 | 含义 | 可追加 | 处理 |
|---|---|---|---|
| `no_evidence` | 完全没有证据 | 是 | 定向检索 |
| `critical_claim_without_support` | 关键结论无支撑 | 是 | 补充检索/计算 |
| `critical_claim_not_verified` | 关键结论未核验 | 是 | 反证检索 |
| `critical_conflict` | 关键冲突 | 是 | 反证/权威源 |
| `noncritical_conflict` | 非关键冲突 | 是（低优先） | 补充说明 |
| `insufficient_information` | 信息不足 | 是 | 定向检索 |
| `missing_calculation`（新增） | 必要计算未完成 | 否（走重跑/人工） | 标记未完成 |
| `missing_input`（新增） | 关键输入缺失 | 否 | 暂停请求用户 |
| `failed_step`（新增） | critical 步骤失败 | 否 | replan 或 stop |
| `unresolved_dependency`（新增） | 依赖未完成 | 否 | 等待/停止 |

### 3.2 缺口来源分层

1. **计划层**：`completionCriteria` 未满足；
2. **证据层**：`research.claims/evidence/conflicts`；
3. **执行层**：`state.steps` 失败/blocked；
4. **输入层**：`goal.missingInfo` 非空。

P3 的评估必须**四层合并**，不能只看证据层。

## 4. 动作决策

### 4.1 六种动作

| 动作 | 触发 | 约束 |
|---|---|---|
| `continue` | 仍有 pending/running | 不改变计划 |
| `append` | 存在可追加缺口且预算允许 | 每轮 1 条，≤2 轮，`searches < limit` |
| `replan` | criticalFailed 且 `replans < limit` | 仅重组依赖 |
| `pause` | 缺关键输入 / 需用户确认 / 证据冲突无法自动判定 | 必须给理由 |
| `complete` | §2.2 全部满足 | 生成阶段报告 |
| `stop` | 预算耗尽 / 取消 / 达到重规划或追加上限 / 非研究任务 | 保存状态 |

### 4.2 优先级（固定）

```
取消 → stop
预算耗尽 → stop
仍有 pending → continue
criticalFailed → replan（未超限）否则 stop
缺失关键输入 → pause
存在可追加缺口且预算允许 → append
完成条件满足 → complete
否则 → stop（含剩余缺口清单）
```

### 4.3 理由要求

每个决策必须返回：

```js
{ action, reason, gaps, details, counts, evidence, resolved, budgetHint }
```

`reason` 为机器码 + 80 字内说明；报告直接引用，不二次生成。

沿用 [planner.expand](file:///D:/Projects/Astrum/core/planner.js#L559-L630)：

- 不新增模板、不改已成功步骤；

### 5.2 上限

- 每轮 1 条；
- 总轮次 ≤ 2（`control.js` 硬编码）；
- 总追加受 `budget.appends`；
- 搜索受 `budget.searches`。

## 6. 重规划

触发与限制见 `P3-02 §8`。补充约束：

1. 重规划前保留原计划（`state.replans`）；
2. 新版本必须重新过 DAG 校验；
3. 重规划后重新计算预算余量；
4. 影响较大的变更（删除 critical 步骤、增加 > 2 步）需用户确认；
5. 超限 → `stop`，不自动继续。

## 7. 进度报告（数据面）

评估结果应产出一份可序列化的 `ProgressSnapshot`：

```js
{
  at, planId, planVersion,
  dimensions: {
    taskCompletion: 0..1,
    goalCoverage: 0..1,
    evidenceCompleteness: 0..1,
    criticalConflicts: number,
    requiredCalcDone: 0..1,
    openQuestions: number,
    budgetRemaining: { ms, searches, appends, recoveries }
  },
  gaps: [{ code, key, claimId?, conflictKey?, text? }],
  action, reason,
  counts: { evidence, claims, conflicts, independentSources }
}
```

存储：写入 `state.events`（仅 `progress.decided` + `action/reason`）与报告数据；**不新增持久化 store**。

## 9. 验收要点

1. 全部成功 → `complete`，报告无缺口；
2. 部分成功 → `stop`/`append`，报告列出缺口；
3. 关键任务失败 → `replan`（未超限）或 `stop`；
4. 可选任务失败 → 不阻断，报告标注；
5. 证据不足 → 至少一次 append，之后仍未解决则 stop；
6. 冲突未解 → 不得 complete；
7. 无限循环防护：append ≤2、replan ≤limit、guard 200；
8. 进度数值可复算，且与 `state` 一致。

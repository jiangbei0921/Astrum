# P4-01 产品需求与功能边界

## 1. 目标

让 P3 已能规划与执行的科研任务，在页面刷新、浏览器崩溃或会话中断后，能够：

1. 找到“状态已保存但未完成”的原任务；
2. 在用户主动确认后，从合法检查点继续执行剩余步骤；
3. 已完成且可安全复用的步骤不重复执行；
4. 非幂等步骤按契约重新执行，绝不把旧检索结果冒充新结果；
5. 全过程保留身份、项目、Skill 版本与权限校验，不出现越权恢复。

## 2. 用户可见需求

| 编号 | 需求 | 验收表现 |
| --- | --- | --- |
| U-1 | 刷新后仍能看到未完成任务 | 启动后出现“有未完成的研究任务”卡片 |
| U-2 | 能看到任务进度与最后保存时间 | 卡片显示 `已完成/总步骤`、阶段、`updatedAt` |
| U-3 | 用户主动选择是否继续 | 不自动执行长任务；点击“继续任务”才恢复 |
| U-4 | 恢复失败要说明原因 | 权限失效、项目归档、检查点损坏、次数超限分别提示 |
| U-5 | 恢复后能看到新进度 | 复用现有答案渲染；已完成步骤不重复出现 |
| U-6 | 暂停与恢复语义清晰 | “已暂停/待审批”不等于“已完成”或“失败” |
| U-7 | 关闭浏览器不承诺后台执行 | 文案明确“状态已保存，重新打开后可继续” |

## 4. 明确不做

1. 不重做 P3 Planner/Scheduler/Runner/Reducer。
2. 不新增 Event Bus、消息队列、事件驱动执行或事件重放。
3. 不新增后端、云数据库、Service Worker 或后台常驻执行。
4. 不新增第三方运行时依赖。
5. 不把 `TaskState` 暴露给最终 answer 或 UI 内部编辑。
6. 不绕过 P0 身份权限与 P2 Skill 审批。
7. 不做自动清理全部历史任务。
8. 不做“恢复即视为任务完成”。
9. 不做跨设备同步。
10. 不做 hypotheses tournament、Optimizer 自改写。

## 5. 功能边界判定

| 场景 | 是否属于 P4 | 说明 |
| --- | --- | --- |
| 刷新后继续未完成步骤 | ✅ | 核心 |
| 已完成幂等步骤复用 | ✅ | reuse |
| 检索步骤恢复时重跑 | ✅ | rerun，按契约 |
| 暂停后恢复 | ✅ | 先写检查点 |
| 待审批步骤恢复 | ✅ | 需要用户审批后再继续 |
| 浏览器关闭期间继续跑 | ❌ | 无后台进程 |
| 多设备同步任务 | ❌ | 纯本地 |
| 自动清理 30 天前任务 | ❌ | 需用户确认后另立需求 |
| 恢复时自动提升预算 | ❌ | Q-4 已定仅手动 |
| 修改历史 Event 内容 | ❌ | 事件只追加 |

## 6. 成功指标

1. 刷新中断后，`EXECUTE` 阶段任务可被列出并恢复。
2. 恢复后已完成幂等步骤 `attempt` 不增加。
3. 恢复后非幂等检索步骤重新执行且 `attempt` 增加。
4. 恢复次数超限时 100% 拒绝并给出可读原因。
5. 跨 Profile / 跨项目恢复请求 100% 拒绝。
6. 检查点损坏时 100% 拒绝自动恢复，原数据不被删除。
7. 数据库升级失败不破坏 v1 数据。
8. 原有 Node 测试全绿，新增 P4 测试全绿。
9. Chrome 真实刷新恢复用例通过。

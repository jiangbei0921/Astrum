# P4-05 恢复流程与幂等性设计

## 1. 权威契约

- `15` §4.1：三种策略 `reuse` / `rerun` / `validate_then_reuse`，由工具 `idempotent` 与 `ttlMs` 推导。
- `15` §4.2：同一任务恢复次数 ≤ 1；超限提示重新提问。
- `15` §4.3：恢复 ≠ 后台执行；必须用户主动选择。

> 与 P3 实现的冲突见 P4-00 §7 C-1/C-2，需用户裁定；本设计按权威契约给出默认方案，并列出可选分支。

## 2. 恢复前校验（17 项）

| # | 校验 | 失败结果 |
| --- | --- | --- |
| 1 | Principal 存在且合法 | `DENIED:NO_PRINCIPAL` |
| 2 | profileId 与记录 owner 一致 | `DENIED:PROFILE_MISMATCH` |
| 3 | 会话未切换（`Security.ensureSession`） | `DENIED:SESSION_CHANGED` |
| 4 | 当前仍可 `task.resume` | `DENIED:<capability>` |
| 5 | ResearchProject 存在且非 archived/deleted | `DENIED:PROJECT_NOT_ACTIVE` |
| 6 | 任务 `projectId` 与项目一致 | `DENIED:PROJECT_MISMATCH` |
| 7 | `schemaVersion===1` 且 `fromJSON` 通过 | `DENIED:SCHEMA_INCOMPATIBLE` |
| 8 | 最新检查点通过完整性校验 | `DENIED:CHECKPOINT_INVALID` |
| 9 | `planId/planVersion` 兼容 | `DENIED:PLAN_VERSION_MISMATCH` |
| 10 | 依赖关系有效 | `DENIED:DEP_INVALID` |
| 11 | 涉及 Skill 仍 published | `DENIED:SKILL_REVOKED` |
| 12 | Skill 版本符合检查点记录 | `DENIED:SKILL_VERSION_MISMATCH` |
| 13 | Tool 仍在 Registry | `DENIED:TOOL_MISSING` |
| 14 | 当前能力权限允许执行 | `DENIED:<capability>` |
| 15 | 任务非 DONE/PARTIAL/FAILED/ABORTED | `VIEW_ONLY` |
| 16 | 恢复次数未达上限 | `DENIED:RECOVERY_LIMIT` |
| 17 | 预算剩余可执行至少一个待办步骤 | `DENIED:BUDGET_EXHAUSTED` |

所有拒绝都必须写入 `AuditLog`，并保留具体 `error` 码；不得统一成“恢复失败”。

## 3. 三种恢复策略

| 策略 | 判定 | 动作 | 现有工具示例 |
| --- | --- | --- | --- |
| reuse | `ok` ∧ `inputHash` 未变 ∧ `idempotent===true` | 保留 `result/outputHash`，`attempt` 不变 | `astro.*`、`kepler.*`、`kb.lookup` |
| rerun | `ok` ∧ `idempotent===false` | 重置 `pending`，`attempt++`，重新执行 | `evidence.search`、`paper.search` |
| validate_then_reuse | `ok` ∧ `ttlMs>0` ∧ `now-retrievedAt ≤ ttlMs` | 校验新鲜度，通过则复用，否则 rerun | `simbad.tap`（ttl 7 天） |

`registry.js` 已声明 `idempotent/ttlMs`，直接使用，不在恢复时猜。

### 3.1 与 P3 实现的差异

P3 `resume` 仅用 `inputHash` 判定复用，导致非幂等检索步骤不重跑。P4 需改为按上表。

**影响测试**：`tools/v1-1-e2e-test.js` E5.3 断言“已 ok 步骤不重复执行”。按契约，只应对幂等步骤成立。实施时需把该断言改为“幂等步骤 attempt 不变，非幂等步骤 rerun”，属于语义修正而非降低标准；需用户批准（P4-10 D-2）。

## 4. 恢复执行流程

```text
resume(taskId):
  1. load record + state + latest checkpoint
  2. run 17 checks
  3. if denied -> return {verdict:'DENIED', error, state}，不修改 state
  4. state.pausedAt = null
  5. state.recoveries += 1; budget.used.recoveries += 1（按裁定上限）
  6. for each step:
       running                 -> pending (rerun)
       paused/waiting_approval -> pending
       ok + strategy=reuse     -> 保留
       ok + rerun              -> pending, 清 result/outputHash
       ok + validate_then_reuse-> TTL 通过保留；否则 pending
       failed + retriable + attempt<retry.max -> pending
       failed + 不可重试        -> blocked
  7. appendEvent('task.recovered', {reason:'resume'})
  8. 写检查点（恢复起点）
  9. saveState（同事务）
 10. runPlan(state.plan, state) -> 现有调度器接管
 11. 结果按现有 PROGRESS/JUDGE/COMPOSE 收尾
```

- 必须保留原 `taskId`，禁止新建“看起来相同”的任务。
- 恢复成功 ≠ 任务完成；后续仍走正式评审。
- 恢复失败保留 state 与最后错误，不删除任何记录。

## 5. 次数计数口径

| 概念 | 是否计数 |
| --- | --- |
| 打开任务列表 | ❌ |
| 点击“继续任务”但校验失败 | ❌（未进入执行） |
| 校验通过并进入 runPlan | ✅ +1 |
| 恢复过程中再次刷新 | 已 +1，下次按剩余额度 |
| 恢复执行失败 | 已 +1，不自动重试 |
| 手动重置计数 | ❌ 不提供入口 |

计数落在 `state.recoveries` 与 `budget.used.recoveries`，随任务持久化；刷新不会重置。

### 5.1 上限冲突

- 契约：≤1。
- P3：L2=1、L3/L4=3。
- 默认方案：P4 统一为 **每任务 ≤1**，修改 `BUDGET_LIMITS` 的 `recoveries` 为 1（L1 仍 0）。
- 备选：保留分档并修订 `15`（需用户明确批准修改权威契约）。
- 未裁定前不得进入阶段 B。

## 6. 幂等与副作用防护

1. 节点执行身份：`taskId + stepId + inputHash + planVersion`。
2. 已有 `result` 且满足策略才允许复用。
3. 对非幂等步骤，即使本地记录 `ok` 也必须重跑。
4. 无法判定是否产生副作用的步骤（无 `result`、无 `outputHash`、工具未声明幂等性）→ 不自动恢复，标记 `NEEDS_USER`。
5. 外部副作用（检索、API）不承诺幂等；恢复时以重跑为准，冲突由后续证据评审处理。

## 7. 失败处理

| 失败 | 结果 |
| --- | --- |
| 校验失败 | `DENIED` + 具体 error；任务保持可查看 |
| 执行中失败 | 走现有 FAILED/PARTIAL；`recoveries` 已消耗 |
| 检查点损坏 | 拒绝自动恢复；提示重新提问；保留数据 |
| 保存失败 | 停止恢复，提示存储异常；不重复执行已跑步骤 |
| 预算不足 | 拒绝，提示预算规则（不自动扩容） |
